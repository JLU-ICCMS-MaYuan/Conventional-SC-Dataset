# 01 去中心化超导数据上传：交互状态与前端逻辑

## React/Vite 落地边界

本文描述未来 React state、事件流、校验、API 触发点和 Material 反馈方式。不定义后端接口细节，不替代本目录 `API接口调整方案.md`。

## 核心状态

- `draftRecord`：当前录入的完整超导记录草稿。
- `activeStep`：当前 Stepper 步骤。
- `structureParseStatus`：未上传、解析中、解析成功、解析失败。
- `duplicateCheckStatus`：未检查、检查中、相同结构、不同结构、无法判断。
- `reviewStatusPreview`：待补充、可提交审核、提交中、提交成功、提交失败。
- `snackbarState`：轻量反馈文案和动作。
- `confirmDialogState`：重复结构、清空草稿、提交审核等确认弹窗。

## 主流程

1. 用户通过 FAB 或 Page Header 主按钮创建记录草稿。
2. 前端要求用户填写 DOI、化学式、压强、Tc 和基础超导参数。
3. 用户上传 CIF/POSCAR，上传 Card 展示 ripple、文件名和解析进度。
4. 前端展示结构解析预览。
5. 用户填写 `structure_source_type` 和 `structure_source_label`。
6. 前端请求后端执行同压强结构比较预览。
7. 同压强相同结构时打开确认 Dialog，提示可能重复。
8. 同压强不同结构时允许提交，并用 warning Chip 提示管理员审核。
9. 不同压强直接视为不同结构样本，不做合并提示。
10. 用户确认后提交整条 `superconductor_records`，成功后显示 Snackbar。

## Material 反馈规则

- 点击按钮、上传区、可选 Chips 时必须有 ripple 或 pressed state。
- 表单提交中使用按钮内 Circular Progress，避免重复提交。
- 保存草稿成功用 Snackbar，不打断流程。
- 结构解析失败在上传 Card 内显示 error text，并保留重新上传入口。
- 重复结构和清空草稿必须使用 Dialog，不只依赖 toast。

## 重复检查反馈

| 后端结果 | 前端提示 | Material 表达 |
| --- | --- | --- |
| 相同结构 | 同一材料同一压强下已存在相同结构 | Warning Dialog + 查看已有记录按钮 |
| 不同结构 | 同一材料同一压强下发现不同结构 | Warning Chip + 可提交审核说明 |
| 无法判断 | 结构比较工具无法稳定判断 | Banner + 人工确认说明 |

重复判断说明必须写清：结构相同判断由 StructurePrototypeAnalysisPackage 完成，不由 hash、坐标四舍五入或文本比较完成。

## 验收标准

- 结构解析、来源填写、同压强重复检查和提交审核互相衔接。
- 不同压强结构不会触发结构合并判断。
- 审核状态始终作用于整条记录，而不是局部参数或局部结构。

## 旧版设计资产融合边界

- PDF 上传沿用旧版“选择文件后进入上传流程”的交互语义，但 demo 只做前端 mock：显示文件名、进度条、解析成功 Snackbar。
- 手动填写沿用旧版“进入结构化记录录入”的语义，但在 demo 中只切换到表单预览，不跳转正式路由。
- 未登录、上传失败、解析失败在正式实现中用 Dialog / Banner / Snackbar 表达；静态 demo 用本地状态模拟。
