# Big Project Overview Maintainer 参考规范

## 1. 目录模型

Overview 默认从简单的两层功能结构开始，但不硬编码目录深度。根目录保存总索引；
每个功能目录保存一个 `README.md`，并包含直属功能文档或下一层功能目录。只有需求、
领域边界或已实现结构确实需要时，才继续创建子目录。

```text
docs/overview/
├── README.md
├── 01-major-feature/
│   ├── README.md
│   ├── 01-subsystem/
│   │   ├── README.md
│   │   ├── sub-feature-a.md
│   │   └── sub-feature-b.md
│   └── feature-c.md
└── 02-major-feature/
    ├── README.md
    └── sub-feature-c.md
```

目录层级遵循最小必要原则：

- 用户或仓库规则明确要求某个子目录时，按要求创建。
- 一组功能形成稳定的领域、子系统或独立工作流边界时，可以创建子目录承载。
- 每个功能目录必须包含 `README.md`，导航其直属文档和直属子目录，并说明组成关系。
- 不为单个普通文档创建无必要的包装目录，不照搬源码目录，也不为未来可能出现的功能预留层级。
- 已有层级能够清晰表达功能时保持现状；不得仅为统一深度而强制展平或加深目录。

功能层级、数量和名称属于项目自身设计，不得硬编码在通用 Skill 中。已有
`docs/overview/README.md` 时以其分类为入口；首次初始化时根据代码和测试提出分类，
获得用户确认后创建。

## 2. 根目录 README 模板

```markdown
# 项目功能总览

## 项目说明

项目解决的问题、主要用户和当前能力边界。

## 大功能目录

| 大功能 | 职责 | 主要依赖 |
| --- | --- | --- |
| [功能一](01-major-feature/README.md) | 当前职责 | 依赖模块 |

## 整体关系

描述大功能之间的数据流、调用关系和共同组成的用户流程。关系复杂时使用 Mermaid。

## 文档维护

说明 Overview 只记录已落地当前事实，并链接项目的 Feature、Debug 或 Issue 入口。
```

## 3. 功能目录 README 模板

```markdown
# 功能分组名称

## 功能边界

说明该功能分组负责什么、不负责什么。

## 直属功能目录

| 功能 | 类型 | 职责 | 依赖 |
| --- | --- | --- | --- |
| [子功能组 A](sub-feature-group/README.md) | 目录 | 当前职责 | 功能 B |
| [功能 B](feature-b.md) | 文档 | 当前职责 | 子功能组 A |

## 功能组成

功能分组或用户流程
├── 子功能组 A
│   ├── 功能 A1
│   └── 功能 A2
└── 功能 B

## 关联关系

说明直属功能及必要后代之间的调用、数据流和状态关系。存在三步以上流程或多个依赖时使用
Mermaid；简单关系使用文字即可。
```

表格负责导航，功能树负责表达组成关系，Mermaid 负责表达复杂流程。`README.md`
不得复制下级功能实现细节。每级 `README.md` 只需完整导航直属子项；更深层内容通过
子目录的 `README.md` 继续导航。

## 4. 功能文档模板

```markdown
# 功能名称

## 功能说明

该功能解决的问题，以及对用户或系统提供的能力。

## 当前行为

已经实现并能够由证据支持的行为。

## 工作流程

输入、处理步骤、输出，以及与其他功能的关系。

## 约束

权限、状态、数据、性能和异常处理等稳定约束。

## 代码与测试

相关代码入口、数据模型、API、配置和测试文件。

## 相关变更记录

链接相关 Feature 或 Debug 文档；不复制其过程内容。

## 已知问题

链接未完成事项的权威入口，不在本文档维护任务状态。
```

## 5. 证据规则

证据优先级：

```text
实际且可信的测试结果
  > 当前代码和配置
  > 已完成的 Feature / Debug 记录
  > 现有 docs/overview/
  > 其他历史文档
```

- 测试没有实际运行或可能已经过期时，只能证明“存在测试覆盖”，不能写成“测试已
  通过”。
- 默认不主动运行测试，避免在 `docs/overview/` 之外产生缓存、数据库或覆盖率文件。
- Feature 和 Debug 文档说明变化背景，最终事实仍需由当前实现核验。
- 旧文档与当前实现冲突时，只更新 Overview，不修改旧文档。
- 无法验证的内容标记为“待核验”，同时列出依据和缺失证据。

## 6. 初始化与增量维护

初始化前必须展示：

- 拟创建的完整递归功能目录树。
- 每层目录的职责、直属子项及新增该层的必要性。
- 功能之间的组成和依赖关系。
- 支持分类的主要代码、测试和配置证据。

普通增量更新可以直接修改现有内容或新增功能文档。用户已明确要求的目录结构视为
对该结构的确认；否则以下结构变化必须先获得用户确认：

- 新增任何功能目录，包括更深层子目录。
- 将功能文档或子目录重新分类到其他父目录。
- 移动、重命名或删除文件。
- 合并或拆分已有功能层级。

Feature 或 Debug 只有在行为已经落地后才能同步。未完成方案、任务清单和排查假设
不得进入 Overview 当前事实。

## 7. 语言规则

1. 首先读取仓库的 `AGENTS.md`、`CLAUDE.md` 或同类项目规则。
2. 项目有明确文档语言要求时严格遵守。
3. 没有规则时跟随现有 `docs/overview/` 的主要语言。
4. 首次初始化且没有既有文档时，跟随用户当前使用的语言。
5. API、代码符号、命令和通用专有名词可以保留原文。

## 8. 验证清单

- [ ] 所有新增和修改文件都位于 `docs/overview/`。
- [ ] 根目录 `README.md` 能导航到所有顶层功能目录或功能文档。
- [ ] 每个功能目录都有 `README.md`，并能导航到全部直属子项。
- [ ] 从根目录出发可以递归到达所有功能文档，不存在孤立目录或断链。
- [ ] 各级功能组成树和关系说明与实际目录一致。
- [ ] 每个当前行为都有代码、配置、测试或可信结果依据。
- [ ] 未实现计划没有被写成当前能力。
- [ ] Feature 和 Debug 仅作为链接与背景来源。
- [ ] 相对 Markdown 链接可以解析。
- [ ] 文档语言符合项目规则。
- [ ] 没有运行测试、修改其他目录或执行 Git 提交。
