# Big Project Planer 参考规则

## 1. 规划层级

总体规划回答“项目为什么做、整体要具备什么能力、系统大体如何分区、先后如何推进”。它比
Issue 和 Spec 更早、更宽，也更少实施细节。

```text
docs/plan/<plan-slug>.md
  -> 总体目标、能力地图、架构方向、跨功能约束、阶段路线

GitHub Issues
  -> 被采纳工作的协作状态、父子关系和交付边界

docs/specs/<issue-number>-<feature-slug>/
  -> 单个 Feature 的需求、技术设计、任务和验收

docs/overview/
  -> 已经实现并可验证的当前事实
```

规划可以提出候选能力和阶段，但不得伪装成已承诺 Issue、可执行任务或已实现事实。

## 2. 设计树主干

按依赖关系展开，而不是机械地一次问完所有主题：

1. **动机与结果**：问题、机会、目标、非目标、成功信号、时间视野。
2. **参与者与价值**：用户、管理员、运营者、外部系统、各方核心任务和冲突。
3. **范围与能力**：能力地图、必须具备、候选能力、明确排除、系统责任边界。
4. **领域与流程**：关键概念、状态、端到端流程、异常路径、人工介入点。
5. **信息与数据**：数据来源、归属、生命周期、质量、隐私、审计、迁移与保留。
6. **架构方向**：模块边界、交互关系、集成方式、部署边界、复用与替换策略。
7. **质量属性**：安全、可靠性、性能、容量、可用性、可维护性、可观测性和合规。
8. **依赖与约束**：既有系统、团队能力、预算、许可证、供应商、平台和交付限制。
9. **阶段路线**：验证性切片、阶段目标、依赖顺序、退出条件、延期或停止条件。
10. **运营与治理**：权限、内容或数据治理、支持、发布、回滚、事故处理和责任归属。
11. **风险与未知**：假设、技术风险、产品风险、组织风险、验证手段和应对策略。
12. **交接边界**：哪些内容应成为 Epic、Feature、Idea、研究项或后续 Spec。

如果某主题确实不适用，记录“不适用”及依据；不得静默跳过。

## 3. Frontier 计算

内部为每个决策维护：`问题`、`前置决策`、`状态`、`答案`、`证据`、`下游分支`。

- 初始 Frontier 只包含不依赖其他用户决策的问题，通常是动机、目标用户和成功定义。
- 用户答案可能新增、删除、合并或改写分支；每轮后必须重算，不沿用固定问卷。
- 两个问题互不依赖时必须放在同一轮；存在依赖时必须分轮。
- 答案只解决部分问题时，将剩余部分保留为新节点，不得擅自补全。
- 用户改变上游决策时，标记所有受影响下游结论为待复核，并重新加入后续 Frontier。
- Frontier 为空的条件是所有适用节点均为已确认或有依据的不适用，且没有未解释假设。

## 4. 提问质量

每个问题必须让用户能快速判断“选什么、会发生什么、代价是什么”：

- 先用大白话说明这项决策实际控制什么，再给出选项。
- 多方案比较必须使用同一场景或同一组数据。
- 每个方案说明具体做法、现有功能或数据的变化、风险和成本、适用条件。
- 推荐答案必须明确，不使用“视情况而定”逃避判断；同时说明推荐成立的前提。
- 区分已查明事实、基于证据的推测和建议。
- 只问需要用户取舍的决策，不让用户代替 Agent 查文件、数记录或确认代码行为。

潜在需求不是“额外功能清单”。只有当某个隐含要求由目标、流程、数据、法规、失败模式或
运营责任推导出来时才提出，并说明推导链。例如：“允许用户删除账户”会解锁数据保留、审计、
关联内容归属和恢复窗口等决策。

## 5. 事实调查

访谈开始前和每轮之间按需检查：

- `AGENTS.md`、README、现有 `docs/plan/`、`docs/overview/`、`docs/specs/` 和开放 Issue。
- 与问题相关的代码、测试、配置、数据模型、部署文件和依赖声明。
- 用户明确放入范围的外部资料或已连接系统。

调查结果只作为事实或选项依据。代码当前这样实现，不等于未来规划必须保持不变；是否兼容由
用户决定。子代理只能执行边界明确的只读事实调查，主 Agent 负责整合结论和提出决策问题。

## 6. 写入质量门

写入前必须同时满足：

- 设计树 Frontier 为空，用户已确认共同理解。
- 目标、范围、非目标、参与者、能力和成功信号彼此一致。
- 关键流程能映射到能力与数据，架构方向能承载关键流程。
- 阶段顺序有依赖依据，每阶段有可判断的退出条件。
- 风险包含触发条件、影响、缓解措施或验证办法。
- 事实、用户决策、建议和假设明确区分。
- 没有落入单个 Feature 的接口字段、类设计或逐文件任务等 Spec 细节。

更新已有规划时保留仍有效内容，并在“决策记录”追加变更原因；相互冲突的旧结论必须修改或
明确标记被取代，不能让两个版本同时作为当前方案。

## 7. 文件与命名

- 路径固定为 `docs/plan/<plan-slug>.md`。
- `<plan-slug>` 使用 2 至 5 个小写英文关键词，以规划主题命名，不使用日期或随机编号。
- 一个文件承载一个可独立讨论的总体规划；只有出现不同目标或不同责任边界时才拆分。
- 规划正文默认使用简体中文；代码符号、命令和通用专有名词可保留原文。
- 不强制创建 `docs/plan/README.md`；仓库已有索引时必须同步其导航。

## 8. 完成检查

- [ ] 文件位于 `docs/plan/`，且没有模板占位符。
- [ ] 文档说明发生什么、为什么、总体如何推进，而不是堆砌抽象名词。
- [ ] 每项关键决策都能追溯到用户确认或事实依据。
- [ ] 潜在需求带有推导理由，没有无依据扩张范围。
- [ ] 能力、架构、数据、阶段、风险和交接项之间没有矛盾。
- [ ] 未把计划描述为已实现事实，未替代 Issue 或 Spec。
- [ ] 所有相对链接均可解析，已有 `docs/plan/` 索引已同步。
