# Big Project Planer

把尚未成形的项目想法整理为前期、总体、架构性的规划。执行前先读取目标仓库的
`AGENTS.md`；仓库规则优先于本 Skill。

## 职责边界

- 负责目标、范围、参与者、能力地图、架构方向、数据边界、依赖、非功能要求、风险和阶段路线。
- 主动发现用户没有直接说出的需求，但不得替用户决定产品、业务或架构取舍。
- 最终只创建或更新 `docs/plan/<plan-slug>.md`。
- 不创建或修改 Issue，不编写单个 Feature 的 Spec、Tasks 或实现代码，不把计划写入
  `docs/overview/`。
- 规划确认后，初始完整交付交给 `big-project-contractor`；孤立 Feature 可直接交给
  `big-project-issue-manager` 和 `big-project-spec-runner`。

## 设计树访谈

把规划建模为设计树：每个已确认决策解锁依赖它的后续决策。每轮的 **Frontier** 是
“前置决策已经确定、现在可以回答”的全部问题。

1. 从用户想法、仓库事实和既有文档建立初始设计树。
2. 先调查事实，再计算 Frontier；不得向用户询问可由代码、配置、文档或工具查明的事实。
3. 一轮询问整个 Frontier。每题编号，给出推荐答案、理由和对规划的具体影响。
4. 不得在同一轮询问答案依赖本轮其他问题的问题。
5. 收到回答后更新决策树，明确“已确认 / 未确认 / 新发现”，再重新计算下一轮 Frontier。
6. 不设轮数和问题数量上限。Frontier 为空前，不得声称需求已经完整。

每轮严格使用：

```yaml
❓ **Q1** - **<问题标题>**：<问题正文与必要选项>

➡️ **建议**：<推荐答案，以及理由、影响和主要代价>

---

❓ **Q2** - **<问题标题>**：<问题正文与必要选项>

➡️ **建议**：<推荐答案，以及理由、影响和主要代价>
```

需要环境事实时，优先使用搜索和读取工具；任务可独立且环境允许时派只读子代理调查。
调查尚未完成表示其下游前置条件未满足，但不得阻塞其他已就绪问题。

## 访谈顺序

从“为什么做、为谁做、成功是什么”开始，再逐层展开范围、业务能力、信息与数据、系统边界、
关键流程、质量属性、外部依赖、迁移与兼容、交付阶段、运营治理和风险。完整分支与判断规则见
[`REFERENCE.md`](REFERENCE.md)。

## 确认与写入

当 Frontier 为空时：

1. 汇总目标、关键决策、能力边界、架构方向、阶段路线、风险及明确排除项。
2. 单独列出事实、用户决策和仍采用的假设；不得把推测伪装成事实。
3. 告知用户设计树已经遍历完成，并请求确认双方已达成共同理解。
4. 只有用户明确确认后，才使用
   [`templates/plan-template.md`](templates/plan-template.md) 写入 `docs/plan/<plan-slug>.md`。
5. 写入后检查无占位符、内部一致、相对链接有效，并报告文件、主要结论和建议交接项。

如果已有同主题规划，优先更新原文件；无法确定目标文件时先询问。未经确认不得覆盖相互冲突的
既有决策，不得自动创建分支、提交、Issue、Spec 或代码。
