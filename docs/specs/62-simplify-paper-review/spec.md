# Feature 规格：简化论文审核弹窗

**GitHub Issue**：[#62](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/62)

**创建日期**：2026-08-31

**状态**：已实现（US1、US2）

## 背景与目标

审核弹窗此前展示大量 AI 解析内容——AI 与用户提交值的三列对照、原文证据引文、同 DOI
候选附件列表。管理员审核时主要需要判定状态并写反馈，这些纯阅读性内容造成信息过载。

本 Feature 移除这些纯展示内容，让弹窗聚焦于「确认分类 → 选状态 → 写意见」。

**关键边界**：弹窗内的「确认材料状态分类」控件**不属于**要移除的展示内容。它是
[Issue #51](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/51)/[#53](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/53)
交付的可编辑功能，管理员通过它修改材料家族与结构家族，并在同一次审核请求中提交。

## 用户场景与验收

### 用户故事 1：管理员快速审核论文（P1，已实现）

管理员点击列表中的审核图标，在弹窗内确认分类、选择审核结果、填写意见后提交。

**独立验收**：弹窗不再显示 AI 对照、原文引文与候选附件，但分类仍可修改。

**验收场景**：

1. **假如** 管理员点击某篇待审核论文的审核图标，**当** 弹窗打开，**那么**：
   - 显示论文标题与 DOI、年份、记录数三个标签
   - 显示「确认材料状态分类」区域，材料家族与结构家族可改选或输入新名称
   - 显示「审核结果」下拉，含通过、拒绝、退回待审核
   - 显示「审核意见」多行输入框
   - 显示取消与确认审核按钮
   - **不显示** AI 与提交值的三列对照、原文证据引文、同 DOI 候选附件

2. **假如** 管理员改选材料家族后选择「通过」并提交，**当** 请求发出，**那么**
   分类变更随同一次审核请求提交，不额外调用目录治理 API。

3. **假如** 管理员选择「拒绝」并填写意见，**当** 提交成功，**那么** 列表中该论文
   状态更新为已拒绝。

### 用户故事 2：编辑页面内审核（P2，已实现）

管理员点击铅笔图标进入编辑页，一边查看和修改论文字段，一边在页面顶部固定区域直接提交审核。

**独立验收**：编辑弹窗顶部有审核控件且不随内容滚走；全部字段仍可编辑。

**验收场景**：

1. **假如** 管理员点击某篇论文的编辑图标，**当** 弹窗打开，**那么** 顶部固定区域显示
   审核结果选择器、审核意见输入框与提交审核按钮，下方仍完整保留标题、DOI、期刊、
   摘要、物性等字段的编辑能力。

2. **假如** 管理员填写审核意见后点击提交审核，**当** 请求成功，**那么** 弹窗关闭、
   列表与统计刷新，该论文状态更新。

3. **假如** 管理员查看审核结果下拉，**那么** 只有「拒绝」与「退回待审核」两项，
   没有「通过」。

**为什么编辑页不提供「通过」**：批准论文要求逐个材料状态确认分类，不完整时后端返回
`409 classification_incomplete`。编辑页没有分类确认区，放开批准只会得到一个必然失败
的按钮。批准仍须走列表中的审核弹窗，那里有分类确认区。这也保住了「批准前必须逐篇
确认分类」这一既有约束。

### 边界与异常场景

- 审核状态沿用现有三值 `pending` / `approved` / `rejected`，不新增状态
- 审核意见可为空，允许不填直接提交
- 审核记录写入 `paper_review_events`，由既有审核接口负责，本 Feature 未改动
- 批准论文时仍执行分类完整性校验，不完整返回 `409 classification_incomplete`
- 权限由后端校验，前端不做判断

## 需求

### 功能需求

- **FR-001**：系统必须移除审核弹窗中的纯阅读性展示，具体为：AI 与用户提交值的三列
  对照（论文类型、理论二级类型、分类理由）、原文证据引文、同 DOI 候选附件列表及其
  下载入口。保留论文标题与 DOI、年份、记录数标签。

- **FR-002**：系统必须在弹窗中提供审核结果选择器，含通过（`approved`）、拒绝
  （`rejected`）、退回待审核（`pending`）三项。

- **FR-003**：系统必须在弹窗中提供多行「审核意见」输入框，内容写入 `review_comment`。

- **FR-004**：系统必须在编辑弹窗顶部提供固定的审核区域，含审核结果选择器、审核意见
  输入框与提交按钮；该区域不得随表单内容滚动而移出视野。

- **FR-005**：编辑弹窗必须保留全部字段的展示与编辑能力，审核区域的加入不得挤占或
  替换任何原有字段。

- **FR-009**：编辑页的审核结果只提供「拒绝」与「退回待审核」，不提供「通过」——
  批准需分类确认，编辑页无该能力。若论文当前为 `approved`，进入编辑页时审核结果
  落到「退回待审核」，避免下拉值不在选项内而显示空白。

- **FR-006**：系统必须保留弹窗中的「确认材料状态分类」可编辑控件，管理员仍可修改
  材料家族与结构家族并在同一次审核请求中提交，不得造成 Issue #51/#53 的能力回退。

- **FR-007**：移除展示内容后，系统必须仍按既有契约提交 `material_states` 与
  `classification_context`（含 `classification_scope`）——这些数据由 `openReview`
  拉取的 detail 与 review-artifact 构造，不可因删除 UI 而一并删除其数据来源。

- **FR-008**：系统必须清理因移除展示内容而失效的前端状态与依赖，不留死代码。

### 关键实体

本 Feature 不新增或修改实体，仅调整既有审核界面的展示范围。

## 成功标准

- **SC-001**：打开审核弹窗后，界面不含「AI 建议、用户提交与原文证据」与
  「同 DOI 候选附件」两个区块。
- **SC-002**：审核结果选择器提供三个选项，任一可选中并成功提交。
- **SC-003**：提交审核后列表状态随即更新。
- **SC-004**：编辑弹窗顶部审核区域使用 sticky 定位，滚动表单时保持可见。
- **SC-005**：编辑弹窗中标题、DOI 等字段仍可定位并编辑。
- **SC-007**：编辑页审核结果下拉不含「通过」选项。
- **SC-006**：`admin-paper-classification-review.test.tsx` 的 2 个用例通过，证明
  分类编辑与一次性提交能力未回退。

## 假设与依赖

- 审核接口 `POST /api/admin/papers/:id/review` 契约不变
- `paper_review_events` 已存在，审核记录由既有逻辑写入
- 前端使用 Material-UI

## 范围外事项

- 不修改后端审核接口与审核状态枚举
- 不新增「需修改」状态（经确认，用「拒绝」+ 意见表达）
- 不实现审核历史查看界面
- 不改动批量审核入口
- 审核意见不支持富文本
