# Feature 规格：修复探索页与社区页长文本正文压过标签的视觉层级

**GitHub Issue**：[#69](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/69)

**创建日期**：2026-08-31

**状态**：已落地

## 背景与目标

探索页详情「研究方法与发现」区块中，「核心发现」的正文内容比「核心发现」这个标签本身
更大也更粗，视觉层级颠倒 —— 正文抢过了标题的位置。

根因是该 `Typography` 未指定 `variant`，默认落到 `body1`（14px），同时又显式写了
`fontWeight={600}`；而标签用的 `caption` 是 12px/600。正文字号大 2px、字重相同，完全
压过标签。

同一区块的「论文总结」用的是 `body2` 且不加粗，详情页 `PaperEditView` 的核心发现也是
`body2` —— 只有探索页与社区页的核心发现是例外，属遗漏而非有意设计。

**业务价值**：
- 可读性：大段文字加粗本身妨碍阅读，字号压过标签则让读者找不到区块边界
- 一致性：同一字段在详情页正常、检索页异常；同一区块内论文总结正常、核心发现异常

## 用户场景与验收

### 用户故事 1：研究者阅读论文的核心发现（优先级：P2）

研究者打开论文详情，希望标签与正文有清晰的层级区分，能一眼看出区块边界。

**优先级理由**：纯视觉问题，不影响数据正确性与功能可用，但用户已明确反馈两次
（换行修复后立即指出字号问题），说明可感知度高。

**独立验收**：核心发现正文不加粗，字号不超过「核心发现」标签。

**验收场景**：

1. **假如** 研究者在探索页打开论文详情，**当** 查看「核心发现」，**那么**：
   - 正文字重为 400（未加粗）
   - 正文字号不大于「核心发现」标签的字号
   - 标签仍保持 600 字重，层级正确

2. **假如** 同一区块存在「论文总结」，**当** 对比两者，**那么** 字号与字重完全一致 ——
   同类内容不应有两种呈现。

3. **假如** 研究者在社区页详情抽屉查看同样字段，**当** 抽屉加载完成，**那么** 呈现与
   探索页一致。

### 边界与异常场景

- **`methodology` 兜底文本**：解析失败或字段为空时显示的 `-`，同样不加粗
- **短值字段不受影响**：DOI、年份、期刊、标题保持 `body1` + 加粗（见 NFR-002）
- **主题变更**：字号断言在 `ThemeProvider` 下测量，主题若调整 `caption` 字号，测试会
  相应反映而非硬编码通过

## 需求

### 功能需求

- **FR-001**：核心发现与论文总结的正文字重必须为 400（不加粗）。覆盖两个页面各两处。

- **FR-002**：正文字号不得大于其标签（`caption` = 12px）。

  说明：改用 `body2`（13px）仍比标签大 1px。用户明确要求「起码大小不能比标签的字大」，
  故显式设为 12px 与标签持平。

- **FR-003**：核心发现与论文总结的字号字重必须一致 —— 同类长文本内容只有一种呈现。

- **FR-004**：探索页与社区页行为一致。

- **FR-005**：`methodology` 的兜底文本（`-` 或原始字符串）不得加粗，共两页面各两处。

- **FR-006**：须有测试断言 computed 字号与字重，且测试须在项目 `ThemeProvider` 下测量
  （MUI 默认 `body2` 是 14px，项目主题覆盖为 13px；不套主题会量到默认值而得出错误结论）。

### 不做的需求

- **NFR-001**：不修改 `frontend/src/theme.ts` 的 variant 定义。主题被全站共用，为一个
  区块的层级问题调整全局字号会波及所有页面。
- **NFR-002**：不改短值字段（DOI、年份、期刊、标题）的 `body1` + 加粗。短值突出、长文本
  平铺是有意的区分：大段文字加粗妨碍阅读，短值加粗则帮助快速定位关键信息。
- **NFR-003**：不改动 `PaperEditView`。它的核心发现一直是 `body2` 不加粗，层级正确。

### 关键实体

**标签与正文的层级约定**：
- 标签：`variant="caption"`（12px / 600）
- 长文本正文：`variant="body2"` + `fontSize: 12`（12px / 400）
- 短值正文：默认 `body1` + `fontWeight={600}`（14px / 600）

## 成功标准

- **SC-001**：核心发现正文的 computed `font-weight` 为 400。
  **已验证**：Vitest 用例断言字重属于 `['400', 'normal', '']`。

- **SC-002**：核心发现正文的 computed `font-size` 不大于「核心发现」标签。
  **已验证**：用例在 `ThemeProvider` 下比较两者 computed 字号。

- **SC-003**：核心发现与论文总结的字号字重完全一致。
  **已验证**：用例断言两节点的 `{fontSize, fontWeight}` 相等。

- **SC-004**：测试能真实捕获缺陷。
  **已验证**：临时还原为 `fontWeight={600}` 且移除 `variant` 后，3 个新用例全部失败；
  恢复后通过。

- **SC-005**：社区页两处已同步。
  **已验证**：产物核对 —— `share-*.js` 中 `pre-wrap` 出现 2 次且均带 `fontSize:12`。

- **SC-006**：TypeScript 编译无错误，既有测试不回退。
  **已验证**：`tsc --noEmit` 通过；全量 110 例中 109 通过（唯一失败为 Issue #63 在建
  代码的 `NewsFeed.test.tsx`）。

## 假设与依赖

- `frontend/src/theme.ts` 的 `caption` 保持 12px；若调整，测试会反映实际关系
- 前端改动需 `npm run build` 输出到 `frontend/static`（本地化开发环境下由宿主机
  `goserver` 与 `backend/main.py` 从该目录提供静态文件，见 Issue #71）

## 范围外事项

- **不改主题定义**：见 NFR-001。
- **不改短值字段**：见 NFR-002。
- **不动 PaperEditView**：见 NFR-003。
- **不做全站排版规范**：本次只修这一个区块的两个字段。「标签与正文的层级约定」值得整理成
  全站规范并用 lint 或组件封装约束，但那是独立议题。
- **不引入 Markdown 渲染**：Issue #68 已记录该决定。
