# 技术调研：News 页面品牌信息与三列独立资讯流

**GitHub Issue**：[ #83](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/83)

**日期**：2026-09-03

## 现状证据

- `frontend/src/pages/NewsPage.tsx` 在 Hero 区渲染机构署名、标题、简介、`Start Exploring` 与 `AI Literature Assistant`；随后渲染三张功能卡。
- `frontend/src/components/NewsFeed.tsx` 目前只维护一个 `{ kind, page }` 查询状态，固定使用 `page_size=20`，并以单列列表和下拉筛选展示自动资讯。
- `GET /api/news/feed` 已接受 `kind`（`news`、`preprint`、`journal_article`）、`page` 和 `page_size`；`page_size=5` 在既有 1–100 的合法范围内。
- 该接口按 `published_at DESC`、`first_seen_at DESC`、`id DESC` 排序，并返回每个请求所需的 `items`、`total`、`page`、`page_size` 与 `sources`。
- 现有详情抽屉、安全外链、空/失败/加载状态都在 `NewsFeed.tsx`，应由抽取后的可复用列组件继续承载。

## 决策

### 决策 1：仅改前端，复用按类型分页 API

**理由**：现有 API 已完整支持每栏所需的类型过滤、页码和页大小。三栏使用三个独立请求即可获得独立总数和分页状态，不需要增加聚合接口或改变采集流程。

**备选方案**：新增一次返回三类内容的后端接口。

**拒绝原因**：会增加后端契约、测试和部署面，但不提供当前需求所需的额外价值。

### 决策 2：每栏拥有封装的独立查询状态

**理由**：`page`、加载、失败、重试和结果必须严格隔离，避免点击一个 `Next` 影响其他两栏。以类型为固定输入的可复用列组件可集中保留列表、分页和详情触发逻辑，消除三份复制代码。

**备选方案**：在父组件持有三个并列状态并复制三段 JSX。

**拒绝原因**：加载、错误、分页和渲染规则会重复，后续修复容易不一致。

### 决策 3：来源状态保留为页面级信息

**理由**：来源状态描述的是共同的采集系统，而非一条或一类资讯。重复显示三次既浪费首屏空间，也会让读者误以为三栏分别采集。

**备选方案**：每栏展示完整来源状态。

**拒绝原因**：信息重复，直接损害“无需滚动查看分页”的首屏目标。

### 决策 4：桌面端三列，窄屏纵向排列

**理由**：三列解决宽屏空白；窄屏继续强行三列会压缩标题、作者与分页按钮。使用响应式网格保持条目和交互控件可读。

**备选方案**：移动端横向滚动三列。

**拒绝原因**：会隐藏内容并破坏移动端的阅读与分页体验。

### 决策 5：首屏基线限定为 1440×900

**理由**：用户的“无需滚轮看到 5 条和 Next”是桌面密度目标，必须有可验证尺寸。不同系统字体、浏览器缩放和移动设备高度无法保证全局无纵向滚动。

**备选方案**：宣称任意视口无滚动。

**拒绝原因**：不可测且会迫使内容在小屏上不可读。
