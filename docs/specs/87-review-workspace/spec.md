# Feature 规格：审核编辑页元数据与成功返回工作台

**GitHub Issue**：[#87](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/87)

**创建日期**：2026-09-03

**状态**：已确认，待实施

## 背景与目标

管理员和超级管理员在论文审核编辑页中无法看到上传者身份，记录数的展示文案也未复用正确的“记录”文案。审核请求成功后，页面只显示“审核已提交”，停留在已完成的编辑页，超级管理员不能直接回到其工作台继续处理下一篇论文。

本 Feature 让审核人员在编辑页明确看到上传者和关联记录数，并在审核成功后立即返回当前角色对应的工作台。

## 用户场景与验收

### 用户故事 1：审核前核对论文来源与记录规模（优先级：P1）

管理员或超级管理员打开论文审核编辑页，在提交审核前查看论文的上传者和关联记录数。

**优先级理由**：来源和记录数量是审核判断的基础上下文。

**独立验收**：详情接口返回 `uploader_name: "author"` 与 `record_count: 2` 时，页面显示“上传者: author”和“记录: 2”。

**验收场景**：

1. **假如** 论文详情有上传者和记录数，**当** 审核编辑页加载完成，**那么** 元数据区显示两项值。
2. **假如** 历史论文没有上传者，**当** 页面加载完成，**那么** 上传者显示 `-`，不显示空白或 `undefined`。
3. **假如** 论文没有关联记录，**当** 页面加载完成，**那么** 记录数显示 `0`。

### 用户故事 2：提交审核后继续处理工作台任务（优先级：P1）

超级管理员或管理员提交审核成功后立即回到自身工作台。

**优先级理由**：审核完成后的编辑页不再是有效工作状态，返回工作台减少额外返回操作。

**独立验收**：超级管理员成功提交“通过”后路由为 `/superadmin`；管理员成功提交后路由为 `/admin`。

**验收场景**：

1. **假如** 超级管理员在编辑页选择“通过”，**当** 审核接口成功响应，**那么** 页面立即导航到 `/superadmin`。
2. **假如** 管理员提交任一审核结果，**当** 审核接口成功响应，**那么** 页面立即导航到 `/admin`。
3. **假如** 审核接口失败，**当** 页面收到错误，**那么** 留在编辑页并显示失败提示。

## 需求

### 功能需求

- **FR-001**：审核编辑页必须在非编辑元数据区展示详情接口返回的 `uploader_name`；缺值时展示 `-`。
- **FR-002**：审核编辑页必须以 `admin.recordsChip` 展示详情接口返回的 `record_count`；缺值时展示 `0`。
- **FR-003**：审核请求成功后，页面必须立即导航到当前角色的工作台：`superadmin` 到 `/superadmin`，其他允许角色到 `/admin`。
- **FR-004**：审核请求失败时，页面必须保持当前位置并显示既有失败提示。
- **FR-005**：新增行为必须保留中文和英文界面可用性，不新增重复翻译键。

## 成功标准

- **SC-001**：前端回归测试证明上传者、零记录和非零记录均按预期渲染。
- **SC-002**：前端回归测试证明超级管理员和管理员的成功审核分别进入正确工作台。
- **SC-003**：前端回归测试证明失败审核不触发导航。
- **SC-004**：前端生产构建通过。

## 假设与依赖

- `GET /api/admin/papers/:id` 已提供 `uploader_name` 和 `record_count`，本 Feature 不改变后端契约。
- 编辑页已有根据当前角色计算的 `workspacePath`，可作为唯一导航事实来源。

## 范围外事项

- 不修改审核权限、审核状态、持久化模型或后端接口。
- 不补写历史论文的上传者数据。
- 不在工作台增加跨页面成功提示。
