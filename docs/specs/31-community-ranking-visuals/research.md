# 技术研究：唯一公开用户名与贡献榜身份

## 决策 1：使用 `ascii_bin` 保证大小写敏感唯一

- **决策**：`users.username` 使用 ASCII 二进制排序规则并建立唯一索引。
- **理由**：用户名字符集限定为 ASCII；二进制排序能让 `Alice` 与 `alice` 在数据库层共存并抵御并发写入。
- **备选方案**：默认 MySQL 排序规则通常大小写不敏感；只在应用层查询无法解决并发竞态。
- **证据**：生产数据库为 MySQL 8.4，现有注册写路径由 Go/GORM 执行。

## 决策 2：迁移使用密码学安全随机数并重试碰撞

- **决策**：每个历史账号生成 `sc_` 加 12 位 `[a-z0-9]`，维护进程内已用集合并查询现存值，碰撞则重试。
- **理由**：不包含邮箱、实名或可推断用户 ID，12 位空间足够大。
- **备选方案**：邮箱泄露隐私；`user_<id>` 可推断规模和顺序；姓名会重复。
- **证据**：用户在澄清中明确选择随机字符串。

## 决策 3：更名资格使用布尔字段并条件更新

- **决策**：历史账号 `username_change_allowed=true`，新账号为 `false`；自助更名使用带资格条件的事务更新。
- **理由**：条件更新可避免同一账号并发提交两次都成功；失败事务不会消耗资格。
- **备选方案**：仅前端隐藏按钮无法阻止直接调用；计数器对“一次机会”没有额外价值。

## 决策 4：超级管理员更名与审计同事务

- **决策**：用户名更新和 `username_change_audit_events` 插入在同一事务执行；只提供读取审计的接口。
- **理由**：任一步失败都不应留下无审计身份变化或孤立审计。
- **备选方案**：应用日志不便稳定查询，且可能因日志轮转丢失。

## 决策 5：保留 `display_name` 作为兼容别名

- **决策**：贡献榜新增 `username`，兼容期继续返回 `display_name=username`，前端只使用 `username`。
- **理由**：避免潜在外部消费者立即破坏，同时消除字段数据来源歧义。
- **备选方案**：立即删除 `display_name` 是不必要的破坏性变更。

## 决策 6：实名保留但不进入客户端身份 DTO

- **决策**：注册可选接收实名并继续保存在现有列；认证、榜单和管理员客户端响应不序列化该字段，邮件称呼改用用户名。
- **理由**：满足选填和不展示要求，同时不执行不可逆历史数据删除。
- **备选方案**：删除列超出范围；继续返回但由前端隐藏仍会造成不必要隐私暴露。
