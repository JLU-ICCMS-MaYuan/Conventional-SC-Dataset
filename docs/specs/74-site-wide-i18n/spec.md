# Feature 规格：全站中英文界面切换，数据层统一英文

**GitHub Issue**：[#74](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/74)

**创建日期**：2026-09-01

**状态**：草稿（2026-09-01 重大范围修订，见澄清记录）

## 背景与目标

SC-Wiki 面向超导材料研究者，用户群体包含不使用中文的研究者，但当前界面全部是硬编码简体中文，非中文用户无法使用。

现状事实：

- 前端 45 个文件共约 2400 处硬编码中文串，`frontend/package.json` 无任何 i18n 依赖，也没有语言上下文或文案字典。
- `material_families`、`structure_families` 两张分类目录表已有 `name_zh` 与 `name_en` 双列，但普通接口只返回规范中文名（见[领域模型与 Schema](../../overview/02_Decentralized_Maintenance_and_Verification/domain-model-and-schema.md)）；用户自建家族的 `name_en` 从不写入。
- 数据库里唯一的中文内容是 LLM 生成的六个叙述字段（`summary`、`keywords_tags`、`methodology`、`key_finding`、`research_motivation`、`knowledge_graph_title`）。论文 `title`、`abstract`、化学式、物性名与单位、DOI 本就是英文。

本 Feature 分两件事：

1. **界面双语**：用户在顶栏头像左侧切换语言，界面文案、固定枚举标签、分类目录名随之切换。
2. **数据层统一英文**：六个叙述字段改为由 LLM 直接产出英文，不再产出中文、不做双语存储。库中既有的中文数据用一次性脚本转换为英文。

**为何数据层不做双语**：这些字段的事实来源是英文论文原文——`summary` 浓缩英文摘要，`methodology` 提取的是 `particle swarm optimization` 这类英文术语，`key_finding` 引用英文正文。先译成中文再存，等于在事实来源与存储之间插入一道有损转换；审核者也无法逐句比对英文原文与中文摘要。统一英文同时消除了双语存储带来的列翻倍、同步状态检测与译文质量治理成本。

## 用户场景与验收

### 用户故事 1：非中文研究者把界面切换为英文（优先级：P1）

不使用中文的研究者打开站点，在顶栏找到语言切换按钮，点击后整站界面变为英文，之后再次访问仍保持英文。

**优先级理由**：这是本 Feature 的最小可用价值。没有切换入口与界面文案翻译，非中文用户完全无法使用系统。

**独立验收**：未登录状态点击切换按钮，导航、按钮、表单标签、提示语、空态文案全部变为英文；刷新页面后仍是英文。

**验收场景**：

1. **假如** 用户首次访问站点且从未选择过语言，**当** 页面加载完成，**那么** 界面显示简体中文，切换按钮标示当前为中文。
2. **假如** 界面当前为中文，**当** 用户点击语言切换按钮的英文一侧，**那么** 当前页面全部界面文案立即变为英文，无需刷新或重新登录。
3. **假如** 用户已切换为英文，**当** 用户刷新页面或关闭浏览器后重新访问，**那么** 界面仍为英文。
4. **假如** 界面当前为英文，**当** 用户查看任意页面，**那么** 语言切换控件明确标示当前生效语言与可切换的目标语言。
5. **假如** 用户在英文界面下浏览任意页面，**当** 该页面完成渲染，**那么** 界面文案不出现中日韩字符（论文原文与用户自建分类家族的中文名除外）。

### 用户故事 2：固定枚举与分类目录名跟随语言（优先级：P1）

研究者在英文界面下填写上传表单或查看论文详情，下拉选项（材料维度、晶系、Tc 方法、论文类型、审核状态、角色、超导类型）和材料/结构家族名称都显示为英文。

**优先级理由**：与故事 1 同属 P1。上传校对与审核表单的主体是这些枚举和分类项，若它们仍是中文，英文界面在核心工作流上不可用。

**独立验收**：英文界面下打开上传校对页，所有下拉选项与分类家族名为英文。

**验收场景**：

1. **假如** 界面为英文，**当** 用户展开材料维度、晶系、Tc 方法、论文类型或审核状态下拉，**那么** 选项文本为英文，且选中后提交的枚举值不变。
2. **假如** 界面为英文且某材料家族由 seed 提供，**当** 用户查看该家族名称，**那么** 显示其规范英文名。
3. **假如** 界面为英文且某材料或结构家族由用户自建、没有英文名，**当** 用户查看该家族名称，**那么** 显示其中文名而不是空白，且不影响该家族的选择与提交。
4. **假如** 用户在英文界面下自建一个新的材料家族，**当** 提交保存，**那么** 该家族被正常创建，中文名为用户输入值。

### 用户故事 3：解析产出英文叙述字段（优先级：P2）

上传者提交 PDF 后，解析产出的六个叙述字段为英文，与论文原文语言一致。

**优先级理由**：排在 P1 之后。界面骨架翻译完成后，数据语言的统一才有意义；且该改动涉及解析链路与存量数据转换，交付周期长于界面部分。

**独立验收**：解析一篇新 PDF，六个叙述字段的内容为英文。

**验收场景**：

1. **假如** 用户上传一篇英文 PDF，**当** 解析完成进入校对页，**那么** 六个叙述字段的内容为英文。
2. **假如** 解析产出的某个字段无原文依据（例如引言未交代研究动机），**当** 查看该字段，**那么** 该字段为空，不产出编造内容。
3. **假如** 上传者提交草稿，**当** 论文落库，**那么** 六个字段以英文持久保存。
4. **假如** 用户查看论文详情，**当** 界面语言为中文或英文，**那么** 这六个字段都显示同一份英文内容，不随界面语言变化。

### 用户故事 4：存量中文数据转换为英文（优先级：P2）

维护者把已入库论文的中文叙述字段一次性转换为英文，使库内数据语言一致。

**优先级理由**：与故事 3 同批交付。若不转换，库内会长期混有两种语言的同一字段，展示层需要写语言判断分支。

**独立验收**：对含中文叙述字段的论文执行转换，之后这些字段为英文。

**验收场景**：

1. **假如** 库中存在中文叙述字段的论文，**当** 执行转换，**那么** 这些字段被替换为对应英文内容。
2. **假如** 某字段本身为空，**当** 执行转换，**那么** 该字段保持为空，不产出内容。
3. **假如** 转换过程中单篇失败，**当** 继续执行，**那么** 其余论文照常处理，最终报告失败清单。
4. **假如** 转换完成并验证无误，**当** 交付收尾，**那么** 该一次性脚本从代码库中删除。

### 用户故事 5：管理员编辑英文叙述字段（优先级：P2）

管理员在审核与编辑页查看并修改六个叙述字段的英文内容，单栏编辑。

**优先级理由**：与故事 3、4 同批。审核者需要能校正 LLM 产出的英文内容。

**独立验收**：管理员打开编辑弹窗，六个字段以单栏英文呈现，修改后保存生效。

**验收场景**：

1. **假如** 管理员打开论文编辑页，**当** 查看六个叙述字段，**那么** 每个字段以单个输入区呈现英文内容，可编辑。
2. **假如** 管理员修改某字段内容，**当** 保存，**那么** 内容持久生效。
3. **假如** 管理员修改 `knowledge_graph_title`，**当** 保存后重新打开，**那么** 改动持久生效——该字段此前不在服务端写入白名单内，编辑会被静默丢弃。

### 边界与异常场景

- 语言偏好读写失败（浏览器禁用本地存储或存储已满）：界面按默认中文渲染并保持可用，切换在当前会话内仍生效，不因存储失败阻断页面。
- 本地存储中的语言值非法（被手工篡改为未知值）：按默认中文处理，不抛错、不白屏。
- 分类目录接口不可用：沿用现有的目录不可用错误提示，语言切换不引入新的失败模式。
- 用户自建分类家族无英文名：英文界面回退显示中文名。这是英文界面下允许出现中文的唯一情形。
- 转换脚本遇到单篇论文失败：跳过并继续，最终报告失败清单，不中断整批。
- 论文原文语言：`title`、`abstract` 与化学式在两种语言下都按原文展示，不翻译、不标注。
- 存量数据中的编码损坏：`papers.id=9` 的 `knowledge_graph_title` 存在双重编码损坏（UTF-8 字节被按 Latin-1 通道写入），无法完整还原。转换脚本按英文重新产出该字段，顺带修复该损坏。

## 需求

### 功能需求

- **FR-001**：系统必须在顶栏用户头像左侧提供语言切换控件，支持简体中文与英文两种语言。
- **FR-002**：语言切换控件必须标示当前生效语言与可切换的目标语言。
- **FR-003**：用户未选择过语言时，系统必须使用简体中文作为默认语言。
- **FR-004**：切换语言必须立即对当前页面生效，不要求刷新页面或重新登录。
- **FR-005**：系统必须在同一浏览器内持久保存用户的语言选择，跨会话生效。
- **FR-006**：语言偏好读写失败或存储值非法时，系统必须回退到默认中文并保持页面可用。
- **FR-007**：全站界面文案（导航、按钮、表单标签与占位符、提示语、错误信息、空态文案、对话框、表头）必须在两种语言下都有对应文本。
- **FR-008**：固定枚举（材料维度、晶系、Tc 方法、论文类型、审核状态、用户角色、超导类型）的显示标签必须跟随语言切换，且其提交值保持不变。
- **FR-009**：材料家族与结构家族的名称必须能按当前语言展示。
- **FR-010**：材料或结构家族缺少英文名时，英文界面必须回退显示其中文名，且不影响该家族的选择与提交。
- **FR-011**：论文解析必须以英文产出六个叙述字段（总结、关键词、研究方法、核心发现、研究驱动力、知识图谱标题）。
- **FR-012**：解析时某叙述字段无原文依据时，该字段必须为空，不得生成无依据的内容。
- **FR-013**：论文提交落库必须以英文持久保存六个叙述字段。
- **FR-014**：六个叙述字段的展示内容不得随界面语言变化，两种语言下都显示同一份英文内容。
- **FR-015**：系统必须提供把存量中文叙述字段转换为英文的一次性能力。
- **FR-016**：转换必须跳过内容为空的字段；单篇失败时跳过并继续处理其余论文，最终报告失败清单。
- **FR-017**：转换验证完成后，一次性脚本必须从代码库中删除。
- **FR-018**：管理员审核与编辑页必须以单栏形式展示六个叙述字段并支持编辑保存。
- **FR-019**：`knowledge_graph_title` 必须可由管理员编辑并持久保存。
- **FR-020**：手工快讯的标题与摘要必须以英文录入，不做双语存储。
- **FR-021**：论文的 `title`、`abstract`、化学式、物性名称与单位在两种语言下都按原文展示，不翻译。

### 关键实体

- **语言偏好**：用户选择的界面语言，取值为简体中文或英文，按浏览器持久保存，未设置时视为简体中文。不属于用户账号数据。
- **论文叙述字段**：论文的六项 AI 解读内容（总结、关键词、研究方法、核心发现、研究驱动力、知识图谱标题）。内容语言统一为英文，不存在语言变体。
- **分类目录项**：材料家族与结构家族的目录条目，具有规范中文名与可空的规范英文名。seed 条目两者齐备，用户自建条目只有中文名。

## 成功标准

- **SC-001**：英文界面下遍历全部页面与主要对话框，界面文案的中日韩字符出现次数为 0（论文原文与自建家族中文名除外）。
- **SC-002**：切换语言后当前页面文案完成更新，无需刷新页面，且不触发重新登录。
- **SC-003**：语言选择在同一浏览器内跨会话保持，重新访问站点时命中率 100%。
- **SC-004**：新解析论文的六个叙述字段内容为英文，中日韩字符出现次数为 0（原文无依据因而为空的字段除外）。
- **SC-005**：转换执行后，库内六个叙述字段的中日韩字符出现次数为 0，失败项有明确清单。
- **SC-006**：管理员修改任一叙述字段后保存并重新打开，内容与保存值一致。
- **SC-007**：`knowledge_graph_title` 的管理员编辑保存成功率 100%（修复既有的静默丢弃缺陷）。
- **SC-008**：交付收尾时代码库中不存在一次性转换脚本。
- **SC-009**：现有上传、审核、检索、社区图表功能在两种语言下行为一致，既有自动化测试全部通过。

## 假设与依赖

- 语言偏好只存浏览器本地，不写入用户账号，因此不支持跨设备同步。理由是避免为一个纯展示偏好新增数据库列与账户接口改动。
- 只支持简体中文与英文两种语言。
- 英文叙述内容由 LLM 直接产出，依赖既有 LLM 配置可用。
- 固定枚举标签在前端维护双语字典，后端枚举值契约不变。理由是这些枚举值稳定且已有前端兜底常量。
- 论文原文为英文，因此叙述字段以英文产出无需翻译中间步骤。
- 依赖 Issue #70 已落地的 `knowledge_graph_title` 字段（Go 模型、详情输出与前端消费均已贯通）。
- 与 [Issue #73](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/73)（顶栏 AI 供应商切换）共享顶栏右侧区域，两者控件位置需协调，功能无重叠。
- [Issue #75](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/75) 与 [Issue #76](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/76) 依赖本 Feature 的语言基建先落地，其新增界面文案直接以双语方式编写。

## 范围外事项

- **数据层双语存储**。六个叙述字段统一英文，不加 `*_en` 列、不做同步状态检测、不做译文治理。见澄清记录 2026-09-01 的范围修订。
- 抓取类资讯（arXiv、Crossref、Phys.org 来源）的处理。这些来源本身产出英文。
- 论文 `title`、`abstract`、化学式、物性名称与单位的翻译。这些内容本就是英文，翻译会破坏与外部数据库的对照关系。
- 第三种及更多语言。
- 按地区格式化日期、数字与单位。
- 运行时按需机器翻译与翻译缓存表。
- 语言偏好跨设备同步与账号级语言设置。
- 顶栏 AI 供应商切换控件本身，由 Issue #73 承担。
- 用户自建分类家族的英文名录入与维护工作流。本 Feature 只保证缺英文名时正确回退。
- 中文用户的 AI 摘要可读性优化。叙述字段统一英文后，中文界面下这部分内容仍是英文；论文原文本就是英文，读者已在读英文语境中。

## 澄清记录

### 2026-09-01

- 问：中英切换要覆盖到哪一层？ → 答：界面文案、固定枚举、分类目录名全部纳入。
- 问：语言选择存在哪里？ → 答：只存浏览器本地存储，不写入用户账号，不支持跨设备同步。
- 问：数据库里的中文字段怎么处理？ → **答（范围修订）**：不做双语存储，六个叙述字段统一改为英文产出。理由是这些字段的事实来源是英文论文原文，先译中文再存是有损转换，且审核者无法逐句比对；统一英文同时消除列翻倍、同步状态检测与译文治理成本。此决定取代了本 Spec 早先版本中「新增 6 个 `*_en` 列 + 指纹快照检测同步状态 + 管理员并排双栏编辑 + 幂等回填脚本」的全部设计。
- 问：存量中文数据怎么处理？ → 答：写一次性脚本转换为英文，转换验证完成后删除该脚本（FR-017、SC-008）。
- 问：手工快讯怎么处理？ → 答：同样只写英文，`news_items` 不加列。
- 问：英文界面下允许出现中文吗？ → 答：仅两种情形——论文原文内容（标题、摘要、化学式），以及用户自建分类家族的中文名回退（FR-010）。
