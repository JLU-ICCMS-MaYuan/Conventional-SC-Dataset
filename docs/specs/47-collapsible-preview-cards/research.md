# 技术研究：AI 临时表单字段卡片渐进展开

## 决策 1：在目标组件内建立局部字段卡片组件

- **决策**：把单张字段卡片的测量、展开状态和渲染封装为 `UploadParsingDetail.tsx` 内部组件。
- **理由**：该交互只有临时解析详情使用；局部组件能隔离 Hook 和状态，同时避免扩大公共 API。
- **备选方案**：新增全局通用卡片组件。拒绝原因是当前没有第二个已确认使用点，会产生过早抽象。
- **证据**：现有字段卡片全部在 `UploadParsingDetail` 的 `group.fields.map` 内渲染。

## 决策 2：以 176 px 内容区作为统一收起高度并测量真实渲染高度

- **决策**：内容内层保持完整布局，比较其 `scrollHeight` 与 176 px 收起高度；外层只在收起时裁切。
- **理由**：176 px 遵循项目 8 px 间距系统，可展示多行候选和首批来源信息，同时明显压缩作者列表或多候选长字段。真实高度可适应中英文、长 DOI、JSON 和响应式换行。
- **备选方案**：使用字符数、候选数量或固定行数判断。拒绝原因是来源和证据由多个块组成，字符阈值不能稳定对应实际高度。
- **证据**：Spec FR-002 要求依据当前可用宽度判断，SC-001 使用长短内容结果验收。

## 决策 3：使用标准按钮和 MUI 收起容器表达状态

- **决策**：只有溢出时显示带“展开/收起”文字和方向图标的 Button，并通过 `aria-expanded`、`aria-controls` 关联内容；内容高度切换复用 MUI 动效能力。
- **理由**：标准按钮天然支持键盘、焦点和可访问名称；正文区域不绑定点击事件，可安全选择复制。
- **备选方案**：整张卡片使用自定义 `onClick` 或直接套用所有字段的 Accordion。前者容易误触且需重造键盘语义，后者会给短字段增加无效控制。
- **证据**：Spec FR-003、FR-005、FR-011、FR-012；项目已使用 MUI Button 与 Accordion。

## 决策 4：按任务和字段身份隔离展开状态

- **决策**：字段组件使用 `taskId + field.path` 作为 React 身份；同一字段在轮询更新时保留实例，切换任务时重新建立实例。
- **理由**：不需要全局状态或持久化即可同时满足动态更新保留和跨任务隔离。
- **备选方案**：父组件维护展开字段集合并在任务变化时手工清空。该方案增加同步分支，且没有跨组件共享价值。
- **证据**：Spec FR-006、FR-009 及 US3 场景 1、4。

## 决策 5：尺寸监听采用渐进增强

- **决策**：每次候选内容渲染后立即测量；浏览器支持 `ResizeObserver` 时监听内容尺寸，缺失时使用窗口 resize 作为回退。
- **理由**：轮询更新需要立即校正，响应式宽度变化需要后续校正；回退保证测试环境和较旧运行环境仍可工作。
- **备选方案**：仅监听 window resize。拒绝原因是候选追加不会触发窗口事件。
- **证据**：Spec FR-009、FR-010、SC-003。

## 决策 6：通过公开 UI seam 执行 TDD

- **决策**：测试只渲染 `UploadParsingDetail`，在 fetch API 边界提供解析响应，并通过角色、可访问名称、展开状态和可见内容观察结果。
- **理由**：测试与用户行为一致，不绑定局部组件名称、测量函数或状态结构。
- **备选方案**：导出溢出函数或快照 DOM。拒绝原因是会测试实现细节，重构时产生无意义失败。
- **证据**：用户已确认测试边界；现有上传工作区测试使用同一公开入口。
