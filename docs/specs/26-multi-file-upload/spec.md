# Feature 规格：正文与附件分组及批量文件上传

**GitHub Issue**：[#26](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/26)
**父 Epic**：[#24](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/24)
**状态**：已确认，待实施

## 目标

一个上传任务表示一篇论文，包含恰好一个正文和任意数量补充材料/附件；浏览器最多并行上传 3 个文件，全部成功后锁定清单并开始解析，最终在一个事务中生成一篇待审核论文及其全部永久文件、分段与证据。

## 用户故事

- **US1**：用户先声明完整文件清单和角色，再并行上传；每个文件独立显示进度与错误。
- **US2**：所有文件完成后系统自动锁定清单并只入队一次；解析开始后如需修改，必须取消并新建任务。
- **US3**：文本提取后、昂贵的分段 LLM 前，对正文与附件的标题、DOI、作者做轻量一致性检查。
- **US4**：明确冲突只警告、不自动重新分组、不阻止解析；提交前必须由用户确认。元数据缺失不算冲突。

## 功能需求

- **FR-001**：角色为 `main/supplementary/attachment`，必须恰好一个 `main`。
- **FR-002**：所有角色只允许 PDF/TXT/MD，每个文件最大 50 MiB。
- **FR-003**：同任务内容哈希完全相同的文件直接拒绝。
- **FR-004**：文件清单先创建，文件按稳定 `file_id` 上传；浏览器并发上限为 3。
- **FR-005**：所有声明文件上传成功后通过原子转换锁定 manifest 并仅 enqueue 一次。
- **FR-006**：锁定后禁止增删、换角色或覆盖文件。
- **FR-007**：一致性检查优先用 PDF 元数据、DOI 正则、标题页和开头文本，不新增完整论文 LLM 调用。
- **FR-008**：提交时一个事务写入 Paper、PaperFile、PaperChunk、证据及物性；任一失败全部回滚。
- **FR-009**：旧 `/api/rag/upload-*` 作为兼容适配层，不再拥有独立状态逻辑。
- **FR-010**：Nginx 对 canonical 文件上传路径使用略高于 50 MiB 的请求体阈值并关闭请求缓冲。

## 成功标准

- 三个并行上传不会丢失 manifest 更新或重复入队。
- 多文件任务只生成一个 Paper，并永久关联所有来源文件。
- 明确冲突必须确认后才能提交；缺失元数据不产生误拦截。
- 事务失败时 MySQL 无半成品，临时任务可继续重试。

## 范围外

- 不支持任意二进制附件、OCR 或解析中动态追加文件。
- 不由系统自动拆分成多篇论文。
