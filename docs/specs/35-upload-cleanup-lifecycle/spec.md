# Feature 规格：上传任务分层清理与待审核快照生命周期

**GitHub Issue**：[#35](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/35)

**创建日期**：2026-08-21

**状态**：已确认，实施中

## 背景与目标

上传任务当前把 Redis 状态、RQ Job、LLM 中间产物、待审核快照、未提交文件和正式论文文件
交给同一清理函数处理，无法准确表达“提交后只删临时数据”“未提交到期后全部删除”和
“审核完成后再删审核快照”三种生命周期。本 Feature 将清理职责分层，保持 Redis 上传任务
与 MySQL 正式论文边界，并修复旧 Worker 状态和部署契约不一致问题。

## 用户场景与验收

### 用户故事 1：提交后立即释放临时资源（优先级：P1）

贡献者提交论文后，任务应从上传中心消失，临时状态和处理中间产物应被删除，但正式文件、
Markdown、论文内容和待审核快照必须继续存在。

**优先级理由**：提交清理错误会直接造成正式数据丢失或无限积累临时数据。

**独立验收**：提交一个包含正文和附件的任务，确认正式数据和文件仍存在，而 Redis、RQ Job
及分段 JSON 已删除，管理员仍能读取审核快照。

**验收场景**：

1. **假如** MySQL 提交事务成功，**当**提交后清理运行，**那么**只删除临时数据并从任务中心移除。
2. **假如**提交响应在返回前丢失，**当**同一用户用相同 task_id 重试，**那么**返回同一个 paper_id。
3. **假如**审核快照写入失败，**当**论文已经提交成功，**那么**不得删除用于恢复快照的中间数据。

### 用户故事 2：审核完成后删除临时审核快照（优先级：P1）

管理员审核 pending 论文时可以查看 AI 原始建议、用户最终提交值和原文证据对比；审核进入
approved 或 rejected 后，该临时快照应删除，不成为永久审计数据。

**优先级理由**：过早删除会破坏审核，永久保留又违反已确认的临时数据边界。

**独立验收**：pending 可读取当前 revision 快照；approved/rejected 事务成功后快照消失；
pending 决定和 revision 不一致不会误删或误读。

**验收场景**：

1. **假如**论文仍为 pending，**当**管理员打开审核页，**那么**返回当前 revision 的审核快照。
2. **假如**审核事务成功进入 approved 或 rejected，**当**执行后置清理，**那么**删除审核快照。
3. **假如**后置删除失败，**当**审核响应返回，**那么**审核结果保持成功并可重试清理。
4. **假如**快照 revision 与论文当前 revision 不一致，**当**请求审核证据，**那么**拒绝把它作为当前证据返回。

### 用户故事 3：未提交任务到期后完整清理（优先级：P1）

failed、duplicate 和 cancelled 任务到期或被主动清理后，所有临时数据、上传文件、Markdown
和重复候选副本都应删除；已被正式论文认领的任何文件均不得删除。

**优先级理由**：该路径同时承担存储回收和正式论文零误删要求。

**独立验收**：分别清理三个终态，验证所有任务文件消失；模拟 Redis 状态过期、MySQL 不可用
和已有永久认领记录，验证清理仍完整或安全延期。

**验收场景**：

1. **假如**未提交终态到期，**当**清理执行，**那么**删除临时数据、任务文件、Markdown 和候选副本。
2. **假如** Redis state 已过期，**当**清理执行，**那么**仍能凭最小清理上下文删除 RQ 数据和候选副本。
3. **假如** MySQL 不可用或存在永久认领记录，**当**准备删除文件，**那么**延期且正式文件删除数为零。
4. **假如**同一清理重复执行，**当**目标已不存在，**那么**保持成功且不扩大删除范围。

### 用户故事 4：重复任务使用稳定 Redis 契约（优先级：P1）

上传任务列表和详情应直接使用 Worker 写入 Redis 的重复结果，不在每次刷新时查询 Paper 表。
旧 Worker 留下的不完整状态通过一次性迁移修复，部署时可检测 API 与 Worker 契约不一致。

**优先级理由**：这是任务中心的事实来源和混合版本部署问题，错误兼容会把 MySQL 依赖引入轮询路径。

**独立验收**：新 duplicate 状态字段完整；任务 GET 在 MySQL 不可用时仍可返回 Redis 状态；
旧状态迁移后具有固定 24 小时截止时间；API/Worker 契约版本不一致时部署检查失败。

**验收场景**：

1. **假如** Worker 发现重复，**当**写入状态，**那么**一次性保存论文状态、动作、原因和 cleanup_at。
2. **假如**任务列表刷新，**当**存在 duplicate，**那么**不会查询 Paper 表。
3. **假如**旧 duplicate 状态存在，**当**一次性迁移执行，**那么**查询 MySQL 一次并原子回填完整状态。
4. **假如** API 与 Worker 状态契约版本不同，**当**执行部署检查，**那么**检查失败并阻止宣称部署完成。

### 边界与异常场景

- 提交清理只能在 MySQL 事务提交后执行，事务失败时不得清理。
- RQ Job 已自然过期、文件已不存在和快照已删除均视为幂等成功。
- 清理目标必须由 task_id 和受约束目录计算，不接受调用者传入任意绝对路径。
- duplicate 的 existing_paper_id 只定位候选目录，不表示本任务已提交，也不阻止清理本任务副本。
- 审核快照不是 PaperEvidence 或 PaperReviewEvent，不永久保存 AI/用户差异。
- 提交后 Redis 已删除时，提交重试必须验证当前用户是论文上传者，不能只凭 task_id 返回论文。

## 需求

### 功能需求

- **FR-001**：系统必须分别提供临时数据清理、未提交文件清理和重复候选副本清理职责。
- **FR-002**：MySQL 提交事务成功后必须删除 Redis state/draft、用户索引、RQ Job 和可确认无用的处理产物。
- **FR-003**：提交成功后必须保留正文、补充材料、附件、正式 Markdown 及正式 MySQL 数据。
- **FR-004**：提交成功后必须保留包含 task_id、paper_id、paper_revision、AI 值、用户值和证据的精简审核快照。
- **FR-005**：approved/rejected 审核事务成功后必须删除审核快照；pending 决定不得删除。
- **FR-006**：审核快照删除失败不得回滚审核结果，系统必须允许幂等重试。
- **FR-007**：审核快照只有 paper_id 和 paper_revision 均匹配当前论文时才可作为当前审核证据返回。
- **FR-008**：未提交终态清理必须删除任务上传目录、组合及分文件 Markdown、全部处理产物和 duplicate 候选副本。
- **FR-009**：删除未提交文件前必须查询 MySQL 永久认领；查询失败或存在认领时必须 fail-closed。
- **FR-010**：安排到期清理时必须保存最小清理上下文，使 Redis state 到期后仍能清理用户索引、RQ Job 和候选副本。
- **FR-011**：所有清理操作必须幂等，并将删除范围限制在 task_id 对应的受管目录和 Redis/RQ 键。
- **FR-012**：Worker 必须一次性把完整 duplicate 结果和固定 24 小时 cleanup_at 写入 Redis。
- **FR-013**：上传任务列表和详情不得为 duplicate 查询 Paper 表；论文打开时由统一论文接口最终鉴权。
- **FR-014**：旧 duplicate 状态必须通过有明确退出条件的一次性迁移修复，不得保留长期读时 MySQL 兼容。
- **FR-015**：上传状态必须包含契约版本，部署检查必须验证 API 与 Worker 使用相同版本。
- **FR-016**：提交响应丢失后的重试必须按 upload_task_id 查询正式论文、验证上传者并返回原 paper_id。

### 关键实体

- **清理上下文**：task_id、user_id、processing_job_id、existing_paper_id、状态更新时间和契约版本的最小快照。
- **待审核快照**：pending 期间使用的 AI 值、用户值和证据对比，绑定 paper_id 与 paper_revision。
- **永久认领**：MySQL 中 Paper/PaperFile 与 upload_task_id 的正式归属，优先于 Redis 生命周期。
- **上传状态契约**：API、Worker 和迁移脚本共同理解的 Redis 字段版本。

## 成功标准

- **SC-001**：提交成功后临时 Redis/RQ/处理中间数据残留数为 0，正式文件和正式数据丢失数为 0。
- **SC-002**：提交响应丢失的重复请求生成新 Paper 的数量为 0，并返回原 paper_id。
- **SC-003**：pending 审核快照可用率为 100%；approved/rejected 后快照清理成功或进入可重试状态。
- **SC-004**：三个未提交终态到期后的受管临时文件残留数为 0。
- **SC-005**：Redis state 缺失和 MySQL 故障场景下正式文件误删数为 0。
- **SC-006**：上传任务列表和详情对 Paper 表的查询次数为 0。
- **SC-007**：新 duplicate 状态完整字段覆盖率为 100%，API/Worker 契约版本不一致可被自动检查发现。
- **SC-008**：指定上传测试目录中的提交、审核、到期、迁移和部署契约测试全部通过。

## 假设与依赖

- #24、#25 提供任务状态机和 24 小时规则；#28 提供统一论文详情鉴权。
- #33 的正式 File/Chunk/Evidence/Review Event 是永久数据，本 Feature 不改变其 Schema 职责。
- 管理员审核仍由 Go Handler 完成，审核成功后调用 Python 的幂等快照清理接口。
- 旧状态迁移只处理迁移执行时仍存在于 Redis 的任务，完成后脚本可重复运行但不进入正常读取路径。

## 范围外事项

- 不将 AI 原始建议与用户修改差异新增为永久 MySQL 表。
- 不迁移两个历史业务数据库或旧论文文件。
- 不改变论文权限矩阵、审核决定逻辑或 Qdrant 单代重建方案。
- 不删除已被正式论文认领的 PDF、附件或 Markdown。
