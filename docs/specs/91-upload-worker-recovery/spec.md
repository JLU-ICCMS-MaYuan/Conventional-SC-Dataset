# Bug 修复规格：上传 Worker 版本漂移恢复

**GitHub Issue**：[#91](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/91)

**创建日期**：2026-09-08

**状态**：已确认

> 本目录是用户明确要求建立的 Bug 修复规格；Issue 类型保持 `type:bug`，不改作 Feature。

## 背景与目标

上传文件保存后，RQ Worker 才会加载并执行解析入口。长期运行的 Worker 可能已经缓存旧版
Python 模块；当磁盘上的新解析入口依赖新符号时，混合版本模块会在业务函数执行前触发
`ImportError`。RQ 2.12 会把该错误降级成 `Invalid attribute name`，此时业务函数内部的失败
处理尚未运行，上传任务会永久停在 `queued / processing`。

本修复必须让本地 Worker 使用当前源码，并保证任何发生在 RQ 任务入口边界的失败都能形成
用户可见、可重试的失败状态，同时恢复本次已经受影响的两条任务。

## 用户场景与验收

### 用户故事 1：解析启动失败后可见且可重试（优先级：P1）

用户上传论文后，即使 Worker 无法导入解析入口，也能看到明确的解析失败状态并重新解析，
而不是一直看到“等待解析”。

**优先级理由**：永久等待会造成数据已上传但无法继续，也没有用户侧恢复入口。

**独立验收**：向真实 RQ 队列投递一个模块导入失败的上传任务，Worker 消费后任务在同一次
失败处理内进入 `failed`，随后既有重试接口允许重新投递。

**验收场景**：

1. **假如**上传任务处于 `queued`，**当**RQ 无法导入任务入口，**那么**任务变为 `failed`，并记录稳定错误码、失败阶段和安全错误摘要。
2. **假如**业务函数已经把任务置为终态，**当**RQ 随后执行异常回调，**那么**回调不得覆盖既有终态及其业务错误。
3. **假如**失败任务仍保存原始文件，**当**用户请求重新解析，**那么**任务重新入队并使用当前 Worker 处理。

### 用户故事 2：本地代码更新后 Worker 自动刷新（优先级：P1）

开发者修改后端 Python 源码时，本地上传 Worker 自动重启并加载当前模块版本，无需记住手动
重启 Worker。

**优先级理由**：本次故障的直接运行条件是 API 支持热重载而 Worker 长期持有旧模块。

**独立验收**：通过本地启动脚本启动 Worker，修改受监视的 Python 文件后确认 Worker 子进程
被替换；随后当前解析入口可成功导入。

**验收场景**：

1. **假如**本地 Worker 正在运行，**当**`backend/` 下 Python 文件发生变更，**那么**旧 Worker 进程被终止并由新进程加载当前源码。
2. **假如**使用 Docker 生产启动命令，**当**本地热重载能力落地，**那么**生产 Worker 命令和并发配置保持不变。

### 用户故事 3：恢复已知受影响任务（优先级：P2）

用户无需重新上传本次故障涉及的原始 PDF，已有任务可以在修复后的 Worker 上重新开始解析。

**优先级理由**：原始文件完整存在，重复上传会浪费用户时间并产生新的任务记录。

**独立验收**：两条已知任务重新投递后，状态离开 `queued` 并实际进入 `extracting` 或后续阶段。

**验收场景**：

1. **假如**两条任务的原始文件仍存在且旧 job 已失败，**当**执行定向恢复，**那么**两条任务获得新 job，并进入真实解析阶段。

### 边界与异常场景

- 无法从 RQ job 参数提取合法 32 位任务 ID 时，只保留 RQ 原生失败记录，不修改任何上传任务。
- 上传任务已经不存在或已过期时，异常回调不得创建替代状态。
- `ready`、`duplicate`、`cancelled`、`submitted` 或已记录为 `failed` 的任务不得被队列级回调覆盖。
- Redis 在异常回调期间不可用时，回调必须记录服务端日志，但不得阻断 RQ 自身的失败入库。
- 本地源码重载只监视 Python 文件，不因上传文件或 `.data/` 产物反复重启。

## 需求

### 功能需求

- **FR-001**：上传 Worker 必须注册队列级异常回调，覆盖业务入口导入失败和入口执行前异常。
- **FR-002**：异常回调必须只处理参数中含合法上传任务 ID 且任务仍处于运行态的 job。
- **FR-003**：队列级失败必须写入 `status=failed`、`processing_status=failed`、稳定错误码、原失败阶段和不含堆栈/凭据的固定错误摘要。
- **FR-004**：队列级失败必须沿用现有终态清理排程，并允许既有 `/retry` 接口恢复。
- **FR-005**：本地开发启动脚本必须监视 `backend/` 下 Python 源码并在变更后重启上传 Worker。
- **FR-006**：Docker Worker 的启动命令、队列名和生产并发行为必须保持不变。
- **FR-007**：系统必须定向恢复任务 `cbed00781290408bb10392dc282ff776` 与 `92127c24cf034ac79845a8055ccc90b8`，且不得删除其原始文件。

### 关键实体

- **上传任务状态**：Redis 中以 `task_id` 标识的短生命周期状态，是用户看到解析进度和恢复能力的事实来源。
- **RQ job**：引用上传解析入口并携带 `task_id`；RQ 原生 job 状态与上传任务业务状态必须在失败时收敛。
- **本地 Worker 监督进程**：监视 Python 源码并管理实际 RQ Worker 子进程，不消费业务任务。

## 成功标准

- **SC-001**：真实 RQ 导入失败回归场景中，100% 的合法运行态上传任务在该 job 失败处理结束前进入 `failed`。
- **SC-002**：队列级回调对已有终态的覆盖次数为 0。
- **SC-003**：本地 Python 源码变更后 10 秒内启动使用当前源码的新 Worker 进程。
- **SC-004**：两条已知任务均获得不同于旧失败 job 的新 job，并至少进入 `extracting` 阶段。
- **SC-005**：上传相关定向测试全部通过，且 Docker Worker 命令契约保持通过。

## 假设与依赖

- 本地环境已经通过项目安装脚本提供 `watchfiles`；该依赖也是当前 Python 热重载的既有依赖。
- 原始上传文件和 Redis 任务状态在 24 小时生命周期内仍存在。
- 现有 `/retry` 状态机是失败任务的唯一正常恢复入口，不新增平行 API。

## 范围外事项

- 不改变 PDF、GROBID、LLM、分段或汇总算法。
- 不设计跨多版本生产集群的滚动发布协议。
- 不自动重试所有未知 Worker 异常，避免形成无界失败循环。
- 不恢复已过期、已清理或原始文件缺失的历史任务。
