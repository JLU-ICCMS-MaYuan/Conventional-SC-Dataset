# Feature 规格：管理员资格申请与审批

**GitHub Issue**：[#42](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/42)

**创建日期**：2026-08-24

**状态**：已确认

## 背景与目标

普通用户注册不再经过人工审批，管理员资格因此需要独立、可追踪且不与注册状态混用的申请流程。本 Feature 允许资料完整的已验证用户一键申请，由超级管理员审批。

## 用户场景与验收

### 用户故事 1：申请管理员资格（优先级：P1）

已验证邮箱且填写姓名和机构的普通用户无需申请理由即可提交申请。

**独立验收**：提交后看到待审核状态和固定资料快照。

**验收场景**：

1. **假如**用户满足条件，**当**提交申请，**那么**系统保存姓名、机构、ORCID 和研究方向快照并进入 pending。
2. **假如**已有 pending，**当**再次提交，**那么**系统拒绝重复申请。
3. **假如**用户修改了资料，**当**查看既有申请，**那么**已提交快照不随当前资料变化。

### 用户故事 2：撤回与重新申请（优先级：P2）

待审核用户可撤回，拒绝或降级后也可以重新申请。

### 用户故事 3：超级管理员审批（优先级：P1）

超级管理员批准后用户成为管理员；拒绝和降级必须填写原因并永久留痕。

### 边界与异常场景

- 审批、撤回和降级并发时只能有一个终态成功。
- 审批时若申请人已封禁、注销或不再是普通用户，必须拒绝。
- 不能通过修改请求体跳过姓名/机构条件或指定目标角色。
- 申请历史不可修改或删除。

## 需求

### 功能需求

- **FR-001**：只有邮箱已验证、账号 active、角色为 user 且姓名和机构非空的用户可申请。
- **FR-002**：申请不要求理由或证明文件，ORCID 和研究方向可选。
- **FR-003**：提交必须保存当时资料快照且每用户最多一个 pending。
- **FR-004**：pending 申请可撤回，不允许直接修改；资料变化后必须撤回重提。
- **FR-005**：只有超级管理员可批准或拒绝，拒绝必须填写原因。
- **FR-006**：批准必须在同一事务中把申请置为 approved 并将角色从 user 改为 admin。
- **FR-007**：拒绝、撤回或被降级用户可以再次申请。
- **FR-008**：超级管理员可将 admin 降级为 user，必须填写原因并记录审计。
- **FR-009**：申请、撤回、批准、拒绝和降级历史必须永久保留。

### 关键实体

- **管理员申请**：包含用户资料快照、状态、审阅人、拒绝原因和各阶段时间。
- **角色治理事件**：记录降级等角色变化的旧值、新值、原因、操作者和时间。

## 成功标准

- **SC-001**：任何并发条件下每个用户的 pending 申请数不超过 1。
- **SC-002**：批准后角色和申请状态不存在不一致中间态。
- **SC-003**：非超级管理员成功审批次数为 0。
- **SC-004**：全部申请生命周期和降级动作均可从永久历史还原。

## 假设与依赖

- 依赖 #39 邮箱验证状态、#40 资料字段和 #38 权限边界。
- 管理员申请审批入口由 #44 超级管理员工作台承载，本 Feature 提供领域与 API 能力。

## 范围外事项

- 注册时申请管理员、申请理由、证明材料、自动审批、管理员审批他人。
