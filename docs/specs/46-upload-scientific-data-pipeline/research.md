# 技术研究：论文上传科学数据结构化

## 决策 1：新草稿以材料状态为聚合边界

**决策**：新草稿使用 `material_states[]`，每项包含材料、条件、报告空间群、一个理论上下文、
一个实验上下文、Tc 列表和普通物性列表。

**理由**：压力、结构对称性、λ、ωlog 和 Tc 都依赖具体材料状态，继续使用扁平物性行会复制
条件并造成材料名混写。

**备选方案**：给旧 `key_properties` 增加更多列。该方案无法表达上下文关系，拒绝。

## 决策 2：旧草稿在边界一次性转换

**决策**：`_normalize_draft` 接受旧 `key_properties`，按材料、压力、空间群和来源类型分流，
但输出只包含新 `material_states`。GET/PUT 复用该归一化，因此未过期的 Redis 草稿无需重跑 LLM。

**理由**：当前用户任务仍在 ready 状态，要求修复后能直接看到正确压力；长期双写会继续扩散旧契约。

## 决策 3：空间群观察属于状态，完整几何仍属于结构模型

**决策**：在 `material_states` 增加
`reported_space_group_symbol/reported_space_group_number`。只有存在结构格式和文本时才创建
`StructureModel`。

**理由**：论文常只报告空间群名称；现有 `StructureModel` 的文本、格式和哈希均必填，伪造几何会
破坏科学真实性。报告空间群描述的是该论文压力/物相状态的对称性声明。

**备选方案**：创建空 CIF 或放宽结构文本非空约束。两者都会把不完整证据伪装成完整结构，拒绝。

## 决策 4：λ 和 ωlog 只进入理论上下文

**决策**：`lambda_ep` 与 `omega_log_k` 保存到 `CalculationContext`；μ* 同理。

**理由**：它们是 Tc 计算上下文参数，#32 已为其建立结构化字段；注册为普通物性会失去方法关联。

## 决策 5：普通物性定义采用确定性代码

**决策**：优先使用 CSV 规范名；未知名称用规范化名称或原始名称 SHA-256 前缀生成稳定
`custom_*` code。Tc、λ、ωlog 和空间群在分流前被排除。

**理由**：`PropertyDefinition` 必填且没有现成 seed 服务；稳定代码可在重复提交和并发校验中复用。

## 决策 6：来源指纹集中生成

**决策**：对实体类型、材料状态键、原始值/单位和 Evidence 规范 JSON 计算 SHA-256。

**理由**：目标 Schema 要求 64 字符指纹且同 revision 唯一，集中算法避免各写入器不一致。

## 决策 7：先构建 Evidence，再写科学实体图

**决策**：在同一事务中先保存文件、Chunk 和 `PaperEvidence`，再持久化材料状态和结果并建立
Tc/普通物性 Evidence 连接。

**理由**：连接表要求双方 ID 及同一 paper revision；当前先写物性后建 Evidence 的顺序无法连接。

## 决策 8：提交错误区分 DOI 重复与其他完整性错误

**决策**：显式 DOI 查重继续返回 409；其他 `IntegrityError` 返回数据完整性错误并保留服务器日志链。

**理由**：把所有数据库约束错误伪装成 DOI 重复会误导用户，也阻碍诊断。
