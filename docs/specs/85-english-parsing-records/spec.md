# Feature 规格：上传解析规范英文值与本地化 AI 建议

**GitHub Issue**：[#85](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/85)

**创建日期**：2026-09-03

**状态**：已确认，待实施

## 背景与目标

#74 已将最终汇总草稿的六个叙述字段定义为英文输出和单语英文存储，但用于 Upload parsing records 的 `CHUNK_SYSTEM_PROMPT` 仍以中文发出。分段记录中的方法、发现、研究材料、分类建议和关系描述可因此成为中文，并在实时预览、候选汇总与正式论文写入间形成语言混杂。

本 Feature 建立两层明确的数据契约：用于选项框、输入框、审核提交和 MySQL 的规范 AI 值始终为英文；仅供 `AI 建议` 展示的副本按用户发起解析时的界面语言生成。论文原文事实和证据维持其输入语言，不做翻译或伪造。

## 用户场景与验收

### 用户故事 1：上传者查看英文解析记录（优先级：P1）

上传者在 Upload parsing records 查看逐段 JSON 和实时只读草稿时，AI 生成内容是英文，能与英文论文术语一致。

**优先级理由**：用户首先看到的中间结果必须遵守最终数据契约。

**独立验收**：上传英文论文后，完成分段的 `methodology`、`key_findings`、分类建议和关系描述均不含中日韩字符。

**验收场景**：

1. **假如** 分段含中文原文引文，**当** AI 输出候选事实，**那么** `quote` 保留中文，但方法、结论和分类名称均为英文。
2. **假如** 分段解析尚未完成，**当** 用户打开只读预览，**那么** 部分草稿中的 AI 生成字段仍遵守英文规则。

### 用户故事 2：审核者查看英文正式值与可读建议（优先级：P1）

用户审核 AI 表单以及管理员查看已提交论文时，选项框和输入框使用同一套英文规范值；其下方的 `AI 建议` 使用发起解析时的中文或英文，且切换当前页面语言不改写已生成建议。

**优先级理由**：语言一致性必须覆盖 Redis 草稿、MySQL 论文和审核流程。

**独立验收**：中文界面发起的任务中，输入框为英文、AI 建议为中文；英文界面发起的任务中，两者为英文。提交后 MySQL 只接收英文规范值。

### 用户故事 3：维护者阻止语言契约绕过（优先级：P1）

LLM 偶发不遵循 prompt 或浏览器回传中文 AI 生成字段时，服务端不会静默将其写入临时或正式数据。

**优先级理由**：prompt 是软约束，不能单独作为数据质量保障。

**独立验收**：向分段/汇总规范化和草稿 API 输入带中文的生成字段，系统返回定位错误或采用明确的重新生成失败路径，且不写入违规数据。

### 边界与异常场景

- `title`、`abstract`、`authors`、化学式、DOI、原始物性 `name_raw`/`value_raw`/单位与任何 `quote` 属于原文事实，不要求英文。
- `summary`、`keywords_tags`、`methodology`、`key_finding`、`research_motivation`、`knowledge_graph_title`，以及分段的研究材料、关系标签、材料/结构家族 AI 建议和关键发现属于规范生成字段，必须英文。
- `ai_original` 是展示专用的建议副本，不得作为提交或持久化的事实来源；它可按任务的 `suggestion_language` 包含中文或英文。
- 固定枚举键（如 `experimental`）和代码值不受语言检测影响。
- 无法从原文可靠生成英文内容时，返回空值；不得回退成中文，也不得翻译证据原文。
- 临时 Redis 快照有 TTL，不回填；正式 MySQL 中已有中文生成字段按 #74 的一次性受控修复原则处理，无法安全修复必须报告而非猜测。

## 需求

### 功能需求

- **FR-001**：`CHUNK_SYSTEM_PROMPT` 必须明确要求所有生成字段以英文输出，并将 JSON 示例中的生成性中文占位改为英文语义说明。
- **FR-002**：`SUMMARY_SYSTEM_PROMPT`、分段候选汇总、`_normalize_draft` 和实时草稿路径必须使用同一字段分类表，不得各自维护不同的语言规则。
- **FR-003**：生成字段在进入分段清单、`partial_draft`、正式草稿和 MySQL 前必须经服务端语言契约验证。
- **FR-004**：对违规生成字段，服务端必须返回字段路径和可操作错误，且不得写入 Redis 草稿或 MySQL；处理任务应走已有失败/重试语义，不得静默丢字段。
- **FR-005**：`UploadParsingDetail` 中展示的分段 JSON、实时只读预览和最终表单必须直接反映已验证的语言契约。
- **FR-006**：原文事实与证据字段必须保持原语言，不被语言验证器拒绝、翻译或改写。
- **FR-007**：为已提交论文中的历史中文生成字段提供一次性、可审计的修复命令；临时任务快照不迁移。
- **FR-008**：创建上传任务时必须持久化 `suggestion_language`（`zh` 或 `en`）。Worker 必须先生成并验证英文 canonical draft，再生成仅用于 `ai_original` 的同语言建议副本；建议副本不能通过或取代英文校验。
- **FR-009**：历史活跃任务可定向修复：将已验证的英文 `ai_values` 写回 canonical draft，旧中文草稿保留为中文 `ai_original`；不得改写 `quote`、`user_values` 或 MySQL 正式数据。

### 关键实体

- **Chunk result**：保存在任务分段清单的 LLM 候选 JSON，并经 `/parsing` 提供给前端。
- **Upload draft**：Redis 中的 `partial_draft` 与最终草稿；用户可编辑，但服务端仍须保护生成字段契约。
- **Paper**：MySQL 正式论文及其 JSON 叙述列；只保存符合契约的生成字段。
- **Source evidence**：`quote`、页面和原文属性，属于不可翻译的事实来源。

## 成功标准

- **SC-001**：受控英文论文样本的分段记录、实时草稿和最终草稿中所有生成字段均无中日韩字符。
- **SC-002**：受控中文论文样本的 `quote`、标题和摘要保持中文原文，同时生成字段为英文。
- **SC-003**：对所有生成字段违规输入，草稿保存和正式提交均拒绝且无部分写入。
- **SC-004**：历史正式论文修复后，已扫描行全部符合英文契约，未能安全修复的行有明确报告。
- **SC-005**：Pb 历史上传任务的输入框显示英文 `summary`、`methodology`、`key_finding` 和 `research_motivation`，而中文 AI 建议仍可核对；其 `quote` 保持原文。

## 假设与依赖

- #74 的“单语英文存储，不加 MySQL 双语列”仍是稳定决策；Redis 审核草稿允许有展示专用 `ai_original` 副本。
- LLM 能基于中文或英文原文直接生成英文归纳；当无依据时允许空值。
- 语言检测仅用于识别生成字段中的中日韩字符，不把它误当作语义质量或英语拼写校验。

## 范围外事项

- 不改界面 i18n 文案、固定枚举或分类目录多语言显示。
- 不翻译原文事实、不增加翻译服务、缓存表或 `*_en` 列。
- 不回填已接近 TTL 的 Redis 历史任务。

## 澄清记录

### 2026-09-03

- 问：原文证据、标题和摘要是否强制英文？→ 答：保持原文，不强制翻译。
- 问：哪些内容必须英文？→ 答：所有 AI 归纳、分类、命名、方法和结论，在分段记录、草稿、审核与正式数据库中一致为英文。
- 问：AI 建议是否也固定英文？→ 答：否。表单规范值和数据库固定英文；中文/英文 AI 建议按用户发起解析时的界面语言生成，原文事实与 `quote` 保持原样。
