# 技术研究：上传解析记录的英文输出与持久化语言一致性

**GitHub Issue**：[#85](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/85)

## R1：Prompt 与服务端验证共同形成语言契约

**决策**：分段和汇总 prompt 都要求英文，同时在服务端以共享字段表检查生成字段。

**理由**：prompt 能提高正常输出质量，但 LLM 不保证服从；只在最终提交校验会让用户先看到、再编辑语言错误的分段记录。验证必须覆盖产生、暂存和提交三个边界。

**备选方案**：只改 `CHUNK_SYSTEM_PROMPT`。拒绝，因为异常 LLM 输出仍可进入 Redis 和最终数据。

## R2：保留原文证据

**决策**：`quote`、标题、摘要、作者和原始数值字段排除在英文验证外。

**理由**：这些值是核对来源而非 AI 结论。强制翻译会破坏“可逐字核对”的证据链，且会伪造非原文内容。

## R3：一次性修复正式数据，不迁移临时快照

**决策**：只对 MySQL 正式论文执行可审计修复，Redis 任务由 TTL 清理。

**理由**：Redis 解析任务是短生命周期状态；为其增加回填会扩大风险且不产生长期价值。正式论文是用户可再次访问的数据，必须收敛。

## R4：规范值与 AI 建议分开保存

**决策**：任务创建时记录 `suggestion_language`。Worker 先生成并验证英文 canonical draft，再单独生成 `ai_original` 展示副本；中文任务的建议为中文，英文任务的建议为英文。

**理由**：输入框值是后续审核和 MySQL 写入的事实来源，必须稳定英文；AI 建议是辅助阅读内容，应匹配用户当时的界面语言。复用同一个对象会让其中一项要求必然失效。

**边界**：展示副本只允许本地化 AI 归纳文本，标题、摘要、作者、化学式、原始数值、单位和 `quote` 直接复制，不能交给模型翻译。
