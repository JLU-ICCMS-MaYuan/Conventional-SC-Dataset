# Feature 规格：审核编辑页补齐超导性质并支持完全编辑

**GitHub Issue**：[#76](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/76)

**创建日期**：2026-09-01

**状态**：草稿

## 背景与目标

管理员审核论文时看不到也改不了超导性质数据。当前编辑弹窗（`frontend/src/pages/AdminPage.tsx:984`）只有论文级字段加一张扁平物性表，而条件化数据模型把科学数据拆到了材料状态之下：Tc 在 `tc_results`、λ 与 ωlog 在 `calculation_contexts`、结构在 `structure_models`，全部挂在 `material_states` 下。审核弹窗（同文件 855 行）也只能确认分类三项（材料家族、维度、结构家族），改不了任何科学数值。

后端同样没有能力：Go 的 `paperUpdateFields`（`goserver/handlers/admin.go:34`）只覆盖论文级列，`keyPropertyUpdateFields` 只覆盖 9 个物性列，其注释明确写着「压强、温度等条件字段属材料状态，不经物性接口修改」。

结果是审核者发现 Tc 数值或压强录错，只能退回让上传者改，无法当场修正。一次错填要经过「退回 → 上传者修改 → 重新提交 → 再次审核」四步。

本 Feature 让管理员在审核编辑页像上传者一样完整校对与修改超导性质，并对已批准论文提供升版重审机制。

## 用户场景与验收

### 用户故事 1：管理员查看完整的超导性质（优先级：P1）

管理员打开待审核论文的编辑页，看到全部材料状态及其下的 Tc、普通物性与结构附件，字段组织与上传校对页一致。

**优先级理由**：这是后续全部编辑能力的基础，且单独交付就有价值——审核者能一次看清全部科学数据再决定通过或退回，不必在多个页面间切换比对。

**独立验收**：打开编辑弹窗，全部材料状态卡片可见，每张卡片含化学式、材料家族、元素种类数、维度、超导类型、晶系、空间群符号与群号、压强，以及其下的 Tc 列表、普通物性列表和结构附件区。

**验收场景**：

1. **假如** 一篇论文有 3 个材料状态，**当** 管理员打开编辑弹窗，**那么** 3 张材料状态卡片全部呈现，可折叠展开。
2. **假如** 某材料状态下有 2 条 Tc 记录，**当** 查看该卡片，**那么** 2 条 Tc 及其数值、方法、区间、代表性标记都可见。
3. **假如** 某材料状态下有普通物性，**当** 查看该卡片，**那么** 物性名称、原始值、单位可见。
4. **假如** 某材料状态下有结构附件，**当** 查看该卡片，**那么** 结构可预览。
5. **假如** 一篇综述论文没有材料状态，**当** 打开编辑弹窗，**那么** 显示无材料状态的空态提示，不报错。

### 用户故事 2：管理员修改待审核论文的超导性质（优先级：P1）

管理员对 `pending` 论文直接修改材料状态字段、增删改 Tc 与普通物性，保存后原地生效。

**优先级理由**：与故事 1 同属 P1，是本 Feature 的核心价值。待审核论文尚未对外公开，修改无外部影响，是最安全也最高频的编辑场景。

**独立验收**：修改待审核论文的任一科学数据字段，保存后重新打开弹窗，改动持久生效，且论文版本号不变。

**验收场景**：

1. **假如** 管理员修改某材料状态的压强值，**当** 保存，**那么** 改动持久生效。
2. **假如** 管理员为某材料状态新增一条 Tc，**当** 保存，**那么** 新 Tc 出现在该材料状态下。
3. **假如** 管理员删除某条普通物性，**当** 保存，**那么** 该物性不再存在。
4. **假如** 管理员修改材料状态的化学式，**当** 保存，**那么** 该材料状态关联到对应化学式的超导体记录。
5. **假如** 论文为 `pending` 状态，**当** 保存科学数据，**那么** 论文的内容版本号保持不变，审核状态仍为 `pending`。
6. **假如** 保存的数据不满足既有校验规则（如压强区间 min 大于 max），**当** 提交保存，**那么** 保存被拒绝并提示具体原因，已有数据不被破坏。

### 用户故事 3：管理员在审核页补传结构附件（优先级：P2）

管理员在审核时发现缺少结构文件，直接在审核页上传 CIF 或 POSCAR，并可删除错误的结构附件。

**优先级理由**：排在 P1 之后。结构附件缺失不阻塞审核判断（可先通过再补），但补传能力能避免为一个附件走完整的退回流程。

**独立验收**：在审核页为某材料状态上传一个 CIF 文件，上传后自动校验并在该材料状态下预览。

**验收场景**：

1. **假如** 管理员为某材料状态上传合法 CIF 文件，**当** 上传完成，**那么** 文件通过校验并在该材料状态下可预览。
2. **假如** 管理员上传格式非法的文件，**当** 上传，**那么** 提示校验失败原因，不写入数据。
3. **假如** 管理员删除某个结构附件，**当** 保存，**那么** 该结构不再关联到材料状态。

### 用户故事 4：管理员修改已批准论文并触发升版重审（优先级：P2）

管理员发现已公开论文的科学数据有误，直接修改；系统自动升版、退回待审核，并明确告知该论文在重新批准前不对外公开。

**优先级理由**：排在 P1 之后，因为它涉及已公开数据的下架与重审，风险高于待审核论文的编辑，需要在 P1 稳定后再交付。

**独立验收**：修改一篇已批准论文的科学数据并保存，论文内容版本号递增、状态回到待审核、社区图表与探索页不再返回该论文。

**验收场景**：

1. **假如** 管理员打开已批准论文的编辑页，**当** 准备保存科学数据，**那么** 界面在保存前明确告知将升版并退回待审核，期间该论文不对外公开。
2. **假如** 管理员确认保存已批准论文的科学数据，**当** 保存成功，**那么** 论文内容版本号递增、已批准版本标记清空、审核状态变为待审核。
3. **假如** 论文已升版为待审核，**当** 未登录用户访问社区图表或探索页，**那么** 该论文的数据不出现在结果中。
4. **假如** 论文已升版为待审核，**当** 非管理员访问该论文详情页，**那么** 无权查看。
5. **假如** 论文已升版，**当** 管理员查看新版本的论文详情，**那么** 正文文件、文本切片与证据锚点完整可用，RAG 检索与证据展示不断链。
6. **假如** 升版后的论文被重新批准，**当** 批准完成，**那么** 论文重新对外公开，且向量索引与知识图谱按新内容重建。
7. **假如** 升版保存过程中任一步失败，**当** 事务回滚，**那么** 论文保持原有版本号、原有审核状态与原有科学数据，仍然对外公开。

### 用户故事 5：上传校对页行为不回退（优先级：P1）

上传者在校对页编辑材料状态的既有体验完全不变。

**优先级理由**：P1。本 Feature 会把上传校对页的材料状态编辑区抽成共享组件供两处使用，重构不得损害既有的上传链路——那是数据进入系统的主路径。

**独立验收**：上传校对页的材料状态编辑、校验定位、折叠交互、AI 建议展示、结构候选面板行为与重构前一致，既有自动化测试全部通过。

**验收场景**：

1. **假如** 上传者在校对页编辑材料状态，**当** 执行重构前可用的任一操作，**那么** 行为与重构前一致。
2. **假如** 提交时校验失败，**当** 后端返回带材料状态序号的错误，**那么** 页面仍能定位到出错卡片。
3. **假如** 材料状态卡片数超过 2 张，**当** 页面加载，**那么** 默认折叠规则与重构前一致。

### 边界与异常场景

- 论文级字段与科学数据分两次保存：论文级字段保存成功而科学数据保存失败时，论文级改动不回滚，错误提示必须指明失败的是科学数据部分。
- 并发编辑：两名管理员同时保存同一篇论文的科学数据时，后保存者覆盖前者。本 Feature 不引入乐观锁（见范围外事项）。
- 科学数据重建期间的原子性：删除旧实体与写入新实体必须在同一事务内，任一步失败则整体回滚，不留下部分删除的中间状态。
- 结构附件的自引用：结构模型存在父子引用关系，重建时需先解开自引用再删除，否则触发外键约束错误。
- 空材料状态：管理员可把论文的材料状态全部删除（综述论文的合法状态），保存不应因此失败。
- 非管理员调用科学数据接口：返回无权限错误。

## 需求

### 功能需求

- **FR-001**：管理员编辑页必须展示论文的全部材料状态，含化学式、材料家族、元素种类数、材料维度、超导类型、晶系、空间群符号与群号、压强字段。
- **FR-002**：管理员编辑页必须在每个材料状态下展示其全部 Tc 记录，含数值、方法、区间与代表性标记。
- **FR-003**：管理员编辑页必须在每个材料状态下展示其全部普通物性，含名称、原始值与单位。
- **FR-004**：管理员编辑页必须在每个材料状态下展示其结构附件并支持预览。
- **FR-005**：管理员必须能修改材料状态的全部展示字段。
- **FR-006**：管理员必须能对每个材料状态增加、修改、删除 Tc 记录。
- **FR-007**：管理员必须能对每个材料状态增加、修改、删除普通物性。
- **FR-008**：管理员必须能删除材料状态下的结构附件。
- **FR-009**：管理员必须能在审核页为指定材料状态上传 CIF 或 POSCAR 结构文件，上传后自动校验并可预览。
- **FR-010**：结构文件校验失败时必须提示原因且不写入数据。
- **FR-011**：管理员必须能增加与删除材料状态。
- **FR-012**：待审核论文的科学数据保存必须原地生效，不改变论文内容版本号与审核状态。
- **FR-013**：已批准论文的科学数据保存必须使内容版本号递增、已批准版本标记清空、审核状态变为待审核。
- **FR-014**：已批准论文升版后，其正文文件、文本切片与证据锚点必须在新版本下完整可用。
- **FR-015**：已批准论文升版后必须不再对外公开，直至重新批准。
- **FR-016**：升版必须记录审核事件，说明版本变更原因。
- **FR-017**：编辑已批准论文时，界面必须在保存前告知将升版并退回待审核。
- **FR-018**：科学数据保存必须在单一事务内完成，任一步失败则整体回滚。
- **FR-019**：科学数据保存失败时，论文级字段的已保存改动不得回滚，且错误提示必须指明失败的是科学数据部分。
- **FR-020**：科学数据保存必须沿用上传提交的既有校验规则，违反时拒绝保存并提示具体原因。
- **FR-021**：非管理员调用科学数据编辑与结构上传接口必须被拒绝。
- **FR-022**：上传校对页的材料状态编辑行为在重构后必须与重构前一致。
- **FR-023**：材料状态编辑界面必须由上传校对页与管理员编辑页共用同一实现。

### 关键实体

不新增实体。本 Feature 复用条件化科学数据模型的既有实体（材料状态、Tc 结果、普通物性、结构模型、计算上下文、实验上下文），并首次实际使用论文内容版本号的递增语义。

- **论文内容版本**：论文科学数据的版本代号。已批准论文的科学数据被修改时递增，使旧版本数据与新版本数据可区分。当前全库论文均停留在初始版本，本 Feature 是该语义的首次真实使用。

## 成功标准

- **SC-001**：管理员编辑页展示的科学数据字段集与上传校对页一致，无字段缺失。
- **SC-002**：待审核论文的任一科学数据字段修改后保存并重新打开，内容与保存值一致。
- **SC-003**：已批准论文保存科学数据后，内容版本号递增且审核状态为待审核，公开查询不再返回该论文。
- **SC-004**：升版后新版本下正文文件、文本切片与证据锚点的可用数量与升版前相同。
- **SC-005**：升版重新批准后，论文重新出现在公开查询结果中。
- **SC-006**：科学数据保存失败后，论文的科学数据与升版状态与保存前完全一致。
- **SC-007**：非管理员调用两个新接口的拒绝率为 100%。
- **SC-008**：上传校对页的既有自动化测试在重构后全部通过。
- **SC-009**：论文的版本号与审核状态在任何操作前后都满足既有的版本一致性约束。

## 假设与依赖

- 依赖 [Issue #74](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/74) 的 i18n 基建先落地，新增界面文案直接以双语方式编写。
- 依赖 [Issue #33](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/33) 已建立的论文版本血缘约束与公开条件语义，实现须遵守其检查约束。
- 与 [Issue #51](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/51) 的材料状态分类目录规则一致，不改动分类批准工作流。
- 论文级字段与科学数据分两个接口保存，不引入跨服务分布式事务。理由是两者分属不同服务，引入分布式事务的复杂度远超收益，且失败语义可通过独立反馈让管理员明确重试范围。
- 已批准论文升版期间对外不可见是预期行为，通过界面提示让管理员知情。
- 升版时正文文件、文本切片、证据锚点与材料状态的版本号由外键级联自动更新，旧版本不再持有这些数据。本 Feature 因此需要一次外键迁移。理由见澄清记录。

## 范围外事项

- 历史版本的浏览与回滚界面。版本血缘数据保留，但不提供查看旧版本内容的入口。
- 并发编辑的乐观锁与冲突提示。当前审核由少量管理员执行，冲突概率低；引入版本号校验会显著增加接口复杂度。
- 修改论文级字段（标题、作者、摘要等）的能力变更。这些字段的编辑走既有接口，本 Feature 不改动。
- 材料家族与结构家族的分类批准工作流。仍按既有规则在审核弹窗逐个确认。
- 跨进程分布式事务。
- 升版后自动重新批准。升版必然回到待审核，需人工重新批准。

## 澄清记录

### 2026-09-01

- 问：审核页的科学数据编辑要不要覆盖已批准论文？ → 答：覆盖。已批准论文也可编辑，保存时自动递增内容版本号并退回待审核，需重新批准才重新公开。
- 问：已批准论文升版时，正文文件、文本切片与证据锚点怎么处理？ → **答（方案修订）**：新增一次外键迁移，建立单向级联链 `papers → paper_files → paper_chunks → paper_evidences` 与平行分支 `papers → material_states`，四条外键改为 `ON UPDATE CASCADE`，删除 `paper_chunks`、`paper_evidences` 到 `papers` 的两条冗余直连外键，`ON DELETE` 保持 RESTRICT。升版时只更新一次 `papers` 的三个版本字段，由 MySQL 在同一事务内级联更新全部血缘数据。

  此决定取代了早先的「手工逐表迁移版本号」方案——该方案在当前结构下不可执行：5 条复合外键全部是 `ON UPDATE NO ACTION`（立即检查的 RESTRICT），先改父表则子行悬空、先改子表则指向不存在的父行，两个方向都在第一条语句失败。而简单地给所有外键加 CASCADE 也不行：MySQL 不允许多条 CASCADE 作用于同一子表的同一列，且实测确认该冲突在建表期不报错、仅在级联更新时抛 1452。

  代价：本 Feature 从「无数据库迁移」变为「需一次外键迁移」；`ON UPDATE CASCADE` 使此后任何 `content_revision` 更新都会静默带走血缘数据。收益：升版从 4 条顺序敏感的 UPDATE 压缩为 1 条，无需顺序推理，且原方案遗漏的 `material_states` 一并纳入。旧版本不再持有血缘数据的代价不变，与范围外事项（不提供历史版本浏览与回滚）自洽。
