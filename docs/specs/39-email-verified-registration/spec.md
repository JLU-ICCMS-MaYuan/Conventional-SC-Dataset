# Feature 规格：邮箱验证注册

**GitHub Issue**：[#39](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/39)

**创建日期**：2026-08-24

**状态**：已确认

## 背景与目标

普通用户注册目前依赖人工审批，已有邮箱验证码界面却没有可用的生产闭环。本 Feature 将注册改为“邮箱验证后立即成为可用普通用户”，并把管理员资格申请从注册流程中彻底分离。

## 用户场景与验收

### 用户故事 1：验证邮箱并开始使用（优先级：P1）

访客注册普通账号、收到验证码并完成验证后自动登录。

**优先级理由**：这是后续用户中心和管理员申请的身份基础。

**独立验收**：使用可接收测试邮件的邮箱完成注册、验证并进入用户中心。

**验收场景**：

1. **假如**邮箱和用户名未被占用，**当**访客提交合法注册信息，**那么**系统创建未验证的普通用户并发送验证码。
2. **假如**验证码有效，**当**用户在 5 分钟内正确提交，**那么**邮箱被标记为已验证，系统自动登录并进入用户中心。
3. **假如**邮箱尚未验证，**当**用户尝试密码登录，**那么**系统拒绝登录并提供继续验证入口。

### 用户故事 2：安全地重发与纠错（优先级：P2）

用户可以在冷却结束后重发验证码，并得到明确的错误、过期和限流反馈。

**独立验收**：验证重发倒计时、旧码失效、尝试次数和发送额度。

**验收场景**：

1. **假如**距离上次发送不足 60 秒，**当**请求重发，**那么**系统返回剩余等待时间。
2. **假如**验证码已过期、已消费或连续错误达到 5 次，**当**再次验证，**那么**系统拒绝该验证码。
3. **假如**邮箱或 IP 超出额度，**当**继续请求发送，**那么**系统返回统一的限流反馈且不泄漏账号是否存在。

### 边界与异常场景

- SMTP 未配置、发送超时或失败时不得假装成功，也不得把验证码写入日志。
- 同一验证码的并发验证最多成功一次。
- 已验证邮箱再次请求验证时返回幂等成功或统一安全反馈，不签发多个独立结果。
- 历史可用账号迁移后不得因缺少邮箱验证标志被锁出。

## 需求

### 功能需求

- **FR-001**：注册必须始终创建 `user`，不得接受客户端指定管理员角色。
- **FR-002**：系统必须在邮件实际发送成功后才进入等待验证状态。
- **FR-003**：验证码必须为 6 位、有效 5 分钟、单次使用且服务端不明文保存。
- **FR-004**：验证码连续错误最多 5 次；重发冷却为 60 秒。
- **FR-005**：每邮箱和每 IP 每小时最多发送 5 次、每天最多 10 次。
- **FR-006**：验证成功必须自动签发登录会话并返回当前用户。
- **FR-007**：未验证邮箱必须被拒绝登录，普通用户验证后不再需要人工审批。
- **FR-008**：注册界面必须移除“申请管理员”及等待人工审批文案。
- **FR-009**：发送、验证与限流错误不得泄漏邮箱是否已注册。
- **FR-010**：生产配置缺失或 Redis 不可用时必须失败关闭。

### 关键实体

- **邮箱验证挑战**：关联规范化邮箱，包含验证码摘要、到期时间、失败次数和单次消费状态。
- **发送额度**：按邮箱和 IP 分别计算小时与自然日窗口。
- **用户**：注册时固定为普通用户；邮箱验证状态与角色、账号状态相互独立。

## 成功标准

- **SC-001**：正常注册路径在一次邮件和一次验证码提交后即可进入用户中心。
- **SC-002**：并发提交同一验证码时成功次数严格为 1。
- **SC-003**：角色注入、验证码重放、错误尝试和发送滥用均由自动化测试阻断。
- **SC-004**：生产日志和数据库中不存在验证码明文。

## 假设与依赖

- Go 服务继续作为生产认证唯一入口；未挂载的 Python 认证路由不启用。
- Redis 用于短期挑战与额度计数；MySQL 保存用户最终验证事实。
- #31 的用户名格式、唯一性和注册时占用规则保持有效。

## 范围外事项

- 邮箱更换、忘记密码、使用用户名登录。
- 管理员资格申请和审批。
