# 技术研究：材料状态多维分类目录

## 决策 1：分类归属 material_states

**决策**：材料家族、元素种类数和材料维度直接属于 `material_states`；结构家族通过关联表属于材料状态。

**理由**：一篇论文可以研究多个材料，同一材料也可以有多个压力和结构状态。论文级 `sc_type` 无法表达这种粒度；全局 `superconductors` 又缺少论文证据和 revision 边界。

**备选方案**：把家族放在 `papers` 或 `superconductors`。拒绝，因为前者限制一篇论文只能有一个值，后者会让一次论文审核修改跨论文共享事实。

**证据**：当前模型为 `Paper(current revision) 1 -> N MaterialState` 和 `Superconductor 1 -> N MaterialState`，`TcResult` 必须属于一个状态。

## 决策 2：使用两套明确目录而不是泛化分类树

**决策**：建立 `material_families`、`structure_families` 及各自别名表；材料维度使用受控枚举，元素数量和压力使用数值字段。

**理由**：本轮只有材料家族和结构家族需要可治理目录。把所有维度装入通用树会失去外键维度约束，并增加普通查询、权限和审核复杂度。

**备选方案**：一个 `classification_terms` 表承载所有维度和层级。拒绝，当前没有父子分类树或跨维度通用查询需求。

## 决策 3：材料家族是领域主分类，不按元素自动推断

**决策**：每个材料状态至多一个主材料家族。重费米子超导体保留为正式家族；只接受论文明确表述、已审核别名或人工审核。

**理由**：`CeCu2Si2` 含铜但核心归类是重费米子超导体。元素组成只能机械计算元素种类数，不能替代领域分类。

**备选方案**：按化学式包含 H/Cu/Fe/Ni/B/C/N 自动分家族。拒绝，会稳定地产生错误归类。

## 决策 4：正式关系只保存目录 ID

**决策**：正式材料状态保存目录外键，API 普通响应返回 `{id, name}`。内部 `code` 稳定存在，但不在普通界面显示；规范中文名、英文名、编码和已审核别名均映射到同一 ID。

**理由**：名称可以调整，ID 和稳定编码不能随显示语言变化。把中文、英文和编码分别保存为正式值会制造双轨数据。

**备选方案**：继续保存自由字符串或让 AI 直接写英文编码。拒绝，无法保证引用完整性、改名和别名治理。

## 决策 5：确定性规范化，不做模糊自动匹配

**决策**：匹配前执行 Unicode NFKC、去除首尾空白、英文小写、连字符/下划线转空格及连续空白折叠，然后只匹配规范名、稳定编码或已审核别名的唯一规范化值。

**理由**：这可以确定性统一 `iron_based` 与登记别名，但不会把相似材料名猜成正式家族。Python 和 Go 使用相同固定测试向量验证规则。

**备选方案**：编辑距离、向量或 LLM 相似度。拒绝，用户明确要求确定性匹配。

## 决策 6：复合名称只解析已确认维度

**决策**：把 `高压氢化物` 的家族部分映射到氢基超导体；压力仍只读取独立的数值或范围字段。未报告数值时不生成压力等级或默认值。

**理由**：高压/低压是条件，不是和氢基并列的材料家族。混入一个字符串后无法可靠筛选或比较。

## 决策 7：待审核建议与正式目录分离

**决策**：未匹配名称写入 `classification_proposals`，状态为 `proposed -> under_review -> resolved|rejected`。处理结论为映射已有项、批准别名、创建正式项或拒绝。普通管理员可映射已有项并提交目录建议；超级管理员执行正式目录变更。

**理由**：允许用户和 AI 提出新名称，但不能让未经审核的字符串成为正式目录项。

**备选方案**：新名称直接入库并标记待确认。拒绝，会让正式目录和未审核候选共享同一事实来源。

## 决策 8：目录治理使用不可变审计事件

**决策**：创建、重命名、停用、启用、合并和别名批准都在同一事务追加 `classification_audit_events`，保存动作、原因、维度、对象和变更前后 JSON。

**理由**：目录改名和合并会影响多篇论文，必须能回答由谁、何时、为什么改变。

## 决策 9：引用工作保留在内部证据层

**决策**：分段解析继续生成 `current_paper|referenced_work` 作用域，用于排除误判；普通草稿、论文 DTO 和正式科学数据不输出 `referenced_materials`。AI 原始分类名称只在待审核建议或管理员分类证据中保留。

**理由**：引用材料不是本文主要研究对象，但完全删除作用域会使后台重新出现误归类且无法审计。

**备选方案**：公开“引用材料”字段。拒绝，不符合用户只解析主要研究对象全部信息的目标。

## 决策 10：旧兼容只存在于读取边界

**决策**：旧草稿 GET 在内存中转换顶层 `sc_type`，响应移除旧字段；PUT 和新 AI 契约拒绝旧字段。旧数据库迁移工具默认 dry-run，只对白名单值和唯一材料状态匹配执行写入。

**理由**：保证未提交草稿可继续工作，同时给兼容分支明确退出点。当前新数据库本身没有旧类型来源。

**备选方案**：长期同时接受旧新格式。拒绝，会让业务逻辑和测试永久维护两套契约。

## 决策 11：服务职责沿用现有边界

**决策**：Python 负责 AI 草稿规范化、旧草稿转换、提交持久化和迁移工具；Go 提供前端目录读取、管理员材料状态编辑、建议审核和超级管理员治理端点。两侧共享数据库约束和规范化测试向量。

**理由**：上传/LLM 主路径已经在 Python，管理员路由和权限中间件已经在 Go。迁移到单一服务超出本 Feature。

## 决策 12：UI 使用共享 MUI Autocomplete

**决策**：新增共享分类选择组件，使用 MUI `Autocomplete`、portal 菜单、加载/失败/空状态和中文规范标签。上传、管理员审核和论文详情复用相同目录类型及显示组件。

**理由**：原生 `datalist` 在浏览器中的候选展开和自由文本状态不可控，且无法表达已审核项与待确认项。

**备选方案**：仅把静态英文值换成中文。拒绝，仍未接数据库，也无法解决别名和审核。
