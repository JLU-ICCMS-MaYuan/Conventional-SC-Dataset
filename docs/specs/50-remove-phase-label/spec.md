# Feature 规格：删除 phase_label 并明确空间群与可扩展分类边界

**GitHub Issue**：[Issue #50](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/50)

**创建日期**：2026-08-24

**状态**：已确认

## 背景与目标

上传材料状态中的 `phase_label` 被界面显示为“物相”，实际经常填写 `Fm-3m` 等空间群名称，和 `reported_space_group_symbol/number` 重复。`clathrate` 是结构家族/拓扑，也不应被写入空间群。目标是删除该结构化字段，保留空间群和数据来源类型的清晰语义，并为未来可审核、可扩展的多维分类体系保留边界。

## 用户场景与验收

### 用户故事 1：按空间群维护材料状态（P1）

作为论文贡献者，我希望材料状态只使用明确的材料、条件和空间群字段，以免把“物相”误填为固相、液相或结构别名。

**独立验收**：上传草稿编辑、保存、提交和正式入库链路不再生成或依赖 `phase_label`；空间群仍可保存。

**验收场景**：

1. **假如**论文报告 `Fm-3m` 和 `R3m` 两个结构，**当**用户保存草稿，**那么**两个空间群状态独立保留。
2. **假如**论文没有空间群但有多个结构候选，**当**系统归一化草稿，**那么**不得静默合并候选。
3. **假如**用户填写理论或实验数据，**那么** `state_kind` 仍区分 `theoretical/experimental/mixed/unknown`。

### 用户故事 2：兼容历史上传（P1）

作为正在处理旧上传任务的用户，我希望旧草稿仍能读取和提交，同时新数据不再继续产生已废弃字段。

**独立验收**：旧草稿含 `phase_label` 时可读取、保存和提交，归一化后忽略该字段；历史原始证据仍可追溯。

### 边界与异常场景

- `Fm-3m`、`R3m` 等空间群只进入专用空间群字段。
- `clathrate`、`high-pressure phase` 等旧值不模糊迁移为空间群。
- 结构化数据库字段删除后，不得再从数据库模型、API 正式 DTO 或新 AI 输出生成该字段。
- 同一材料、压力和 `state_kind` 下的不同空间群不得合并。
- 空间群是结构事实，不进入未来分类树。

## 需求

### 功能需求

- **FR-001**：系统必须从新上传草稿、编辑器、归一化、保存、提交和持久化契约中删除 `phase_label`。
- **FR-002**：系统必须从 Python 模型、Go 模型、数据库列、相关索引和 Schema 测试中删除 `phase_label`。
- **FR-003**：系统必须保留并校验 `reported_space_group_symbol/number`，群号范围为 1–230。
- **FR-004**：系统必须保留 `state_kind`，用于区分理论、实验、混合和未知数据来源。
- **FR-005**：系统必须按材料、压力、`state_kind` 和报告空间群区分有空间群的材料状态；没有空间群时不得静默合并多个结构候选。
- **FR-006**：系统必须在兼容窗口内忽略旧草稿中的 `phase_label`，新草稿不得产生该字段。
- **FR-007**：系统不得把历史 `phase_label` 值自动迁移为空间群；原始证据或原始 JSON 中已有的文本继续保留。
- **FR-008**：本 Feature 不得把 `clathrate` 加入现有 `sc_type`，未来分类体系必须另行设计。

### 关键实体

- `Superconductor`：保存具体化学计量材料及材料家族基础信息。
- `MaterialState`：保存论文 revision 下材料的压力、温度、磁场、空间群和 `state_kind`。
- `StructureModel/structure_candidates`：保存完整结构和多个候选结构，不以空间群替代结构文本。
- 原始 Evidence/JSON：保留论文原文中未结构化迁移的历史文字。

## 成功标准

- **SC-001**：前端、Python、Go、Alembic 和新草稿契约中不再有结构化 `phase_label`。
- **SC-002**：上传草稿、保存、提交和入库回归测试覆盖完整链路并通过。
- **SC-003**：两个不同空间群在同材料同压力下保留为两个可审查状态，零静默合并。
- **SC-004**：旧草稿兼容测试通过，且新请求体和 AI 输出不包含 `phase_label`。
- **SC-005**：未来分类边界被文档化为多维、层级、可审核、可版本化设计，空间群不参与分类树。

## 假设与依赖

- 现有 reported space group 字段是空间群事实的主契约。
- `state_kind` 与空间群属于正交维度，不能互相替代。
- 现有运行库迁移需遵循 fresh Schema guard 和部署流程；本 Feature 不自动转换旧业务库中其他旧表。
- 分类词典另建 Feature Issue，由注册用户或管理员提出，其他管理员审核后生效。

## 范围外事项

- 不实现未来多维分类词典、分类审核界面或专家分类内容。
- 不重构铜基、铁基、镍基等领域分类。
- 不将 `clathrate` 写入 `sc_type` 或空间群字段。
- 不修改 `state_kind` 的枚举语义。

## 澄清记录

### 2026-08-24

- 问：删除范围？→ 答：完整删除结构化 `phase_label`，包括 UI、AI、Python/Go 模型、数据库列和索引；历史原始证据保留。
- 问：状态区分？→ 答：材料 + 压力 + `state_kind` + 空间群（有则使用）；无空间群时不静默合并候选。
- 问：`state_kind` 是否删除？→ 答：保留，用于区分理论/实验/混合/未知来源。
- 问：`clathrate` 是否迁移？→ 答：不迁移为空间群，不加入现有 `sc_type`；未来作为结构家族分类另行设计。
- 问：分类体系治理？→ 答：注册用户和管理员可提出，其他管理员确认后生效；支持多维、父子层级、生命周期和历史保留。
- 问：本 Feature 是否实现未来分类？→ 答：否，分类体系另建独立 Feature Issue。
