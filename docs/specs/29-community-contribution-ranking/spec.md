# Feature 规格：社区贡献排行榜

**GitHub Issue**：[#29](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/29)

**创建日期**：2026-08-20

**状态**：已确认

## 背景与目标

SC-Wiki 已能关联论文上传者、当前审核人和用户，但社区页面尚未公开呈现贡献规模与贡献者排名。本 Feature 在社区页面增加贡献参与人数、上传贡献榜、审核贡献榜和当前登录用户排名，以可见反馈鼓励持续贡献，同时不公开邮箱等敏感信息。

## 用户场景与验收

### 用户故事 1：查看社区贡献榜（优先级：P1）

访问者进入社区页面后，可以看到贡献参与人数，以及审核通过上传数和有效审核次数各自排名前 20 的贡献者。

**优先级理由**：公开榜单是本 Feature 的核心价值，且不依赖登录状态。

**独立验收**：使用包含已通过上传、审核历史和无贡献用户的数据集访问社区页面，核对人数、两个 Top 20、同分顺序和公开字段。

**验收场景**：

1. **假如** 数据库存在上传或审核贡献，**当** 访问者打开社区页面，**那么** 页面显示去重参与人数及上传榜、审核榜各前 20 名。
2. **假如** 两名用户贡献数相同，**当** 生成榜单，**那么** 较早完成当前累计贡献数的用户排名靠前；仍相同则按用户 ID 升序稳定排序。
3. **假如** 用户仅注册但没有符合口径的贡献，**当** 生成统计，**那么** 该用户不计入参与人数，也不进入榜单。

### 用户故事 2：查看我的全量排名（优先级：P2）

登录用户可以分别看到自己的上传和审核排名，即使自己未进入公开 Top 20；未登录访问者不显示个人排名。

**优先级理由**：个人反馈增强参与感，但公开榜单可在没有该能力时独立交付。

**独立验收**：以 Top 20 内、Top 20 外、零贡献三类账号访问社区页面，核对个人排名区域。

**验收场景**：

1. **假如** 登录用户的某项排名超过 20，**当** 页面加载完成，**那么** 页面仍显示该项全量名次和贡献数。
2. **假如** 登录用户某项没有贡献，**当** 页面加载完成，**那么** 页面明确显示“暂无排名”和 0 次，而不伪造末位名次。
3. **假如** 访问者未登录，**当** 页面加载完成，**那么** 响应和界面均不包含个人排名。

### 用户故事 3：获取最新榜单（优先级：P3）

榜单每小时自动重新获取；用户也可以点击刷新按钮立即查询数据库最新结果，并看到最后更新时间和结果状态。

**优先级理由**：数据时效性重要，但不阻断榜单基础展示。

**独立验收**：控制时间并新增贡献，验证一小时自动刷新和按钮强制刷新分别更新结果与时间。

**验收场景**：

1. **假如** 页面持续打开，**当** 距上次成功获取满一小时，**那么** 页面自动重新请求榜单。
2. **假如** 缓存中的榜单尚未过期，**当** 用户点击“刷新榜单”，**那么** 系统绕过缓存读取数据库最新结果。
3. **假如** 刷新失败，**当** 页面已有成功结果，**那么** 保留旧结果并提示失败；页面没有旧结果时显示错误状态和重试入口。

### 边界与异常场景

- 参与人数按“至少有一篇当前审核通过的上传，或至少有一条有效审核历史”的注册用户去重。
- 上传榜只计算当前 `review_status = approved` 且有上传者的论文；待审核、拒绝、撤回、处理失败记录不计数。
- 每次实际提交通过、拒绝或退回修改的审核结论产生一条审核历史；单篇、批量审核中的每篇论文分别计一次。
- 请求重试、重复点击，或没有新增审核意见且结论与当前状态完全相同的提交，不新增审核历史。
- 同一审核人对同一论文的不同有效审核轮次分别计数；审核历史不可因论文后续状态变化而改写。
- 旧数据没有完整审核历史，迁移只为当前具有审核人和审核时间的论文回填一条可识别的历史记录，不推测更早审核次数。
- 数据库、缓存或认证信息不可用时返回明确错误，不返回部分计算且冒充完整结果。
- 公开榜单只返回真实姓名、派生头像文本、排名和贡献数，不返回邮箱、角色、审批状态或内部认证信息。

## 需求

### 功能需求

- **FR-001**：系统必须按已审核通过的上传和有效审核历史，对注册用户去重计算贡献参与人数。
- **FR-002**：系统必须生成审核通过上传数前 20 名的上传贡献榜。
- **FR-003**：系统必须生成有效审核历史次数前 20 名的审核贡献榜。
- **FR-004**：榜单必须按贡献数降序、达到当前累计数的时间升序、用户 ID 升序生成稳定名次。
- **FR-005**：系统必须为通过、拒绝或退回修改的每次有效审核写入一条不可变审核历史，批量审核按论文逐条记录。
- **FR-006**：系统不得为请求重试、重复点击，或无新增审核意见且状态未变化的提交重复写入审核历史。
- **FR-007**：公开榜单响应只能包含展示名称、派生头像文本、排名和对应贡献数。
- **FR-008**：系统必须在请求携带有效登录身份时返回该用户两项全量排名和贡献数；零贡献项返回无名次和 0 次。
- **FR-009**：未登录请求必须可获取公开榜单，但不得获得个人排名。
- **FR-010**：默认榜单结果必须最多缓存一小时，并携带结果生成时间。
- **FR-011**：用户必须能通过刷新操作绕过榜单缓存并立即读取数据库最新结果。
- **FR-012**：社区页面必须展示参与人数、两个 Top 20、登录用户个人排名、最后更新时间、加载、空数据和失败状态。
- **FR-013**：自动刷新失败时，页面必须保留最近一次成功结果并允许再次手动刷新。
- **FR-014**：系统必须为已有论文中可确认的当前审核人和审核时间回填一条迁移审核历史，并将其标记为回填来源。

### 关键实体

- **审核历史**：一次有效审核动作，关联论文、审核人、审核结论、审核意见、发生时间、来源和幂等标识；创建后不可修改或删除。
- **贡献排行项**：某用户在一种贡献类型下的排名、展示名称、派生头像文本、贡献数和达到当前累计数的时间。
- **贡献榜单快照**：参与人数、上传 Top 20、审核 Top 20 和结果生成时间；登录请求可附加当前用户两项排名。

## 成功标准

- **SC-001**：在包含至少 25 名贡献者及同分数据的验收数据集中，参与人数、两个 Top 20 和个人全量排名与人工 SQL 核对结果 100% 一致。
- **SC-002**：公开榜单响应中敏感字段泄露测试全部通过，邮箱、密码摘要、角色及审批状态均不可见。
- **SC-003**：每个有效单篇或批量审核动作恰好新增一条对应审核历史，定义的重复操作新增 0 条。
- **SC-004**：榜单在页面打开后可见，并在每小时自动刷新或手动刷新成功后显示新的生成时间；失败时已有结果不丢失。
- **SC-005**：后端统计、排序、Top 20、个人排名、审核历史幂等和隐私测试全部通过，前端生产构建通过。

## 假设与依赖

- 用户公开名称使用现有 `real_name`；头像使用名称首字符派生，不增加头像存储字段。
- “退回修改”沿用后端允许的 `pending` 审核结论；只有从其他状态实际退回或新增审核意见时才计为有效审核。
- 审核历史用于贡献计数和审计，不因论文删除而级联删除；论文删除后保留其审核事件的论文 ID 快照。
- Redis 可用于共享缓存；Redis 不可用时允许直接查询数据库，但不得把失败结果缓存为成功结果。
- 当前主要部署链路为 React/Vite → Go Gin → MySQL/Redis。

## 范围外事项

- 积分、勋章、奖励、兑换和反作弊评分体系。
- 日榜、周榜、月榜、历史排名趋势和升降变化。
- 帖子、评论、关注、私信等论坛功能。
- WebSocket 或服务端持续推送。
- 从旧数据推断数据库中不存在的历史审核轮次。

## 澄清记录

### 2026-08-20

- 问：贡献参与人数如何定义？ → 答：至少有一篇审核通过上传或至少完成一次有效审核的注册用户去重数。
- 问：榜单如何刷新？ → 答：页面每小时自动刷新；用户可点击按钮立即读取最新数据库结果。
- 问：榜单如何拆分与排序？ → 答：上传和审核分别取前 20；同分者优先达到当前数量者靠前。
- 问：上传贡献统计哪些记录？ → 答：只统计审核通过并正式进入公共数据库的上传记录。
- 问：Top 20 之外是否显示本人排名？ → 答：登录用户始终显示两项个人排名。
- 问：审核榜统计最终审核人还是审核动作？ → 答：统计每个审核人的有效审核次数，需要保留审核历史。
- 问：同一审核人重复审核同一论文如何计数？ → 答：不同有效审核轮次分别计数；无变化重复提交和请求重试不计数。
