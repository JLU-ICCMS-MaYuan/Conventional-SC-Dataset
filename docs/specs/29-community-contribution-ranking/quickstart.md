# Quickstart：验证社区贡献排行榜

## 前置条件

- MySQL 与 Redis 可用，数据库已执行最新 Alembic 迁移。
- Go API 和前端已按项目现有方式启动。
- 准备至少 25 个贡献用户，其中包含同分用户、仅上传用户、仅审核用户和零贡献用户。

## 自动验证

在 `goserver/` 执行：

```bash
go test ./...
```

在 `frontend/` 执行：

```bash
npm run build
```

预期：命令退出码均为 0；后端测试覆盖统计口径、稳定排序、Top 20、本人排名、审核事件、防重和敏感字段。

## 场景 1：匿名查看公开榜单

1. 不登录访问 `/share`。
2. 核对参与人数等于上传贡献者与审核贡献者的去重并集。
3. 核对上传榜、审核榜各最多 20 人，数量降序且同分顺序稳定。
4. 检查网络响应不含 `email`、`password_hash`、`role`、`is_approved` 和 `current_user`。

## 场景 2：登录用户查看 Top 20 外排名

1. 使用排名超过 20 的贡献账号登录并访问 `/share`。
2. 确认公开榜单仍只有 20 人。
3. 确认“我的排名”显示该账号的准确全量排名与贡献数。
4. 使用某项零贡献账号验证该项显示“暂无排名”和 0 次。

## 场景 3：自动刷新和即时刷新

1. 记录页面“最后更新时间”。
2. 在另一个账号完成一次有效上传审核或审核操作。
3. 在一小时内普通重新请求，确认允许命中原快照。
4. 点击“刷新榜单”，确认贡献数和生成时间立即更新。
5. 保持页面打开满一小时，确认自动发起下一次获取。
6. 暂停后端后触发刷新，确认旧榜单仍保留并出现失败提示。

## 场景 4：审核历史与防重

1. 对同一论文提交一次带新 `review_request_id` 的审核，确认事件数增加 1。
2. 原样重试相同请求，确认事件数不增加。
3. 不带请求键、状态与意见均不变地重复提交，确认事件数不增加。
4. 修改审核意见或进入新的有效审核轮次，确认事件数增加 1。
5. 批量审核 N 篇论文，确认每篇各新增 1 条事件。

## 回归检查

- 管理员仍可完成单篇和批量审核。
- 论文当前审核状态、审核人和审核时间仍正确更新。
- 社区原有 Tc-Pressure、Tc-Year 图表和详情抽屉仍可使用。
