# 技术研究：社区贡献排行榜

## 决策 1：以不可变审核历史作为审核榜事实来源

- **决策**：新增 `paper_review_events`，每次有效审核在更新论文当前状态的同一事务中插入一条事件。
- **理由**：`papers.reviewed_by_user_id` 只表示当前最终审核人，无法表达多个审核人和多轮审核。
- **备选方案**：继续按当前审核人聚合；会丢失历史劳动，与已确认口径冲突。
- **证据**：`goserver/models/models.go` 的 `Paper` 只有单个 `ReviewedBy`；`goserver/handlers/admin.go` 与 `goserver/handlers/stats.go` 会覆盖该字段。

## 决策 2：以请求幂等键和业务无变化判断共同防重

- **决策**：前端为一次提交生成 `review_request_id`；数据库对其建立唯一约束。缺少该字段的兼容客户端仍可提交，但当状态不变且没有新增审核意见时不产生事件。
- **理由**：唯一请求键能处理网络重试，业务无变化判断能处理旧客户端重复点击。
- **备选方案**：仅用时间窗口去重；可能误伤真实短间隔审核，也不能可靠识别跨进程重试。
- **证据**：当前单篇和批量审核接口没有幂等标识，且会直接覆盖论文审核字段。

## 决策 3：使用一条聚合查询生成排名基础数据

- **决策**：分别按审核通过上传与审核事件聚合用户贡献数和最后一个计数事件时间，再按数量降序、时间升序、用户 ID 升序排序；服务层计算名次、Top 20 和本人项。
- **理由**：避免现有 `AllUsers` 的 N+1 查询；稳定排序可复现且便于测试。
- **备选方案**：逐用户 Count；实现直观但随用户数线性增加查询次数。
- **证据**：`goserver/handlers/stats.go:AllUsers` 当前每名用户执行两次 Count。

## 决策 4：共享结果缓存一小时，手动刷新显式绕过

- **决策**：公共榜单快照使用 Redis、TTL 一小时；`refresh=true` 绕过读取并覆盖缓存。个人排名由同一最新全量聚合结果裁剪，缓存中不保存按用户拆分的敏感响应。
- **理由**：满足每小时被动刷新和即时主动刷新，同时避免缓存大量用户专属键。
- **备选方案**：前端只做一小时轮询且后端每次查库；多客户端会造成重复聚合开销。
- **证据**：`goserver/cache/cache.go` 已支持 JSON 缓存和 TTL。

## 决策 5：公开端点采用可选认证

- **决策**：新增只解析有效 Bearer Token、无 Token 时放行的可选认证中间件。无效 Token 返回 401，避免静默降级导致用户误以为本人无排名。
- **理由**：同一公开契约需为登录用户附加本人排名，又不能阻止匿名访问。
- **备选方案**：拆成公共和登录两个端点；会重复请求和聚合逻辑。
- **证据**：当前 `AuthRequired` 对缺少 Token 的请求直接返回 401，不能用于公开榜单。

## 决策 6：数据库迁移同时服务 Go 与 Python 模型

- **决策**：使用 Alembic 新增表和索引，并在 Go GORM 模型中声明对应结构；迁移对当前有审核人和审核时间的论文回填一条 `backfill` 事件。
- **理由**：仓库以 Alembic 管理主库结构，Go 是排行榜和审核的主要写入链路。
- **备选方案**：依赖 GORM AutoMigrate；部署行为不明确，无法提供可审查回填。
- **证据**：`alembic/versions/` 保存主库迁移，Overview 指明 GORM 与 SQLAlchemy 共用 MySQL。

## 决策 7：头像使用名称首字符派生

- **决策**：接口返回 `avatar_text`，取清理后显示名称的首个 Unicode 字符；不新增头像 URL。
- **理由**：现有用户模型没有头像字段，当前 Feature 不需要引入上传和对象存储。
- **备选方案**：新增头像上传；超出榜单范围并增加安全与存储成本。
