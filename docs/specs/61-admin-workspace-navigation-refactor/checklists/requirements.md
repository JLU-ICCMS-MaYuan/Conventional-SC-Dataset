# 需求质量检查表：管理员工作台导航改为卡片式入口

**目的**：审查导航重组需求的完整性，尤其是可访问性与「删除入口后原功能是否仍可达」。

**创建日期**：2026-08-31

**Feature**：[spec.md](../spec.md)

## 完整性

- [x] CHK001 删除 Tabs 后，原每个 Tab 对应的功能是否都仍有入口？
  是。FR-004 列出 5 个可点击卡片，覆盖原「论文审核、用户与权限、图表管理、快讯管理」
  四个 Tab；原「概览」Tab 本身即卡片页，不再需要独立入口。
- [x] CHK002 两种角色的可见卡片是否分别列明？
  是。FR-003（管理员 2 张）与 FR-004（超管 6 张）。
- [x] CHK003 是否规定了不可点击的卡片及理由？
  是。「当前角色」为身份展示，无目标页面（边界场景）。
- [x] CHK004 可访问性是否列为需求而非隐含期望？
  是。FR-005 明确要求键盘可达与按钮语义。**这一项最初仅写「hover 效果」，
  遗漏键盘与读屏**，补充后才发现原实现用带 onClick 的 Card 并不可达。

## 清晰度与可度量性

- [x] CHK005 「视觉反馈」是否可验证？
  是。FR-005 拆为 hover 反馈与可聚焦、可 Enter 激活三项具体行为。
- [x] CHK006 名称一致性是否给出判据？
  是。FR-006 指明卡片名与目标页面名一致，并举出「论文总数 vs 论文审核」为反例。
- [x] CHK007 加载中状态是否明确？
  是。FR-007 要求显示占位符而非 `0`，并在边界场景说明理由。

## 一致性与覆盖

- [x] CHK008 是否与 Issue #62 的改动冲突？
  两者同改 `AdminPage.tsx`：#61 删 Tabs 会使依赖 `getByRole('tab')` 的测试失效，
  需同步更新为卡片入口。已在 plan 实施步骤中列出。
- [x] CHK009 SC 是否可用自动化验证而非仅靠肉眼？
  是。SC-001 可 grep，SC-004 可用 `getByRole('button', { name })` 断言。
- [x] CHK010 是否明确不改动各功能视图自身？
  是。范围外事项第一条。

## 备注

- 本检查表检查需求文本质量，不测试代码或实现行为。
- CHK004 是本 Feature 的关键收获：需求初稿只写「hover 效果」，把可访问性当成样式
  问题。补齐为键盘可达后，才暴露出「带 onClick 的 Card 无按钮语义」这一实现缺陷。
