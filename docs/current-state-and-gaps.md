# 当前功能现状与数据库承接差距

## 1. 结论摘要

先给结论：当前系统在数据库层面更偏向“文献采集与审核系统”，还不是“学术互动社区系统”。

当前 SQLite 数据模型已经能够稳定支撑以下主流程：
- 首页元素检索
- 元素体系页文献浏览
- 用户注册登录
- 文献上传与批量导入
- 管理员审核与全局管理
- 图表展示开关
- JSON 级数据导入导出

但对于文档中后半部分设想的互动能力，数据库层目前基本没有承接：
- 点赞
- 评论
- 弹幕
- 热度排序
- 数据库文件级上传下载

换句话说，当前数据库已经足够支撑“采集、整理、审核、展示”，但还没有开始支撑“互动、沉淀、社区化传播”。

## 2. 当前数据库的实际定位

当前数据库文件是 `data/superconductor.db`，由应用启动时自动建表并初始化基础元素数据。

它当前承担的职责是：
- 保存元素基础数据
- 保存元素组合体系
- 保存文献主记录
- 保存文献下的多组物理参数
- 保存文献截图
- 保存普通用户、管理员、超级管理员账号
- 保存邮箱验证、审批状态、审核状态与审核意见
- 保存文献是否进入首页图表的显示开关

它不是：
- 通用内容社区数据库
- 点赞评论平台数据库
- 独立对象存储系统
- 数据库文件上传下载平台

## 3. 数据库核心表与业务职责映射

### 3.1 `elements`
- 用途：保存 118 个化学元素基础信息
- 支撑功能：首页周期表渲染、元素合法性校验
- 当前定位：基础字典表

### 3.2 `compounds`
- 用途：保存标准化后的元素组合体系
- 关键字段：`element_symbols`、`element_list`、`element_id_list`
- 支撑功能：`only / combination / contains` 三种检索模式
- 当前定位：元素体系检索核心表

### 3.3 `users`
- 用途：保存普通用户、管理员、超级管理员账号
- 关键字段：`is_admin`、`is_superadmin`、`is_approved`、`is_email_verified`
- 支撑功能：注册、登录、邮箱验证、管理员审批、后台权限控制
- 当前定位：统一身份与权限表

### 3.4 `papers`
- 用途：保存文献主记录
- 支撑功能：文献详情、检索、上传、审核、后台管理、图表展示开关
- 关键点：`compound_id + doi` 有唯一约束，保证同一元素体系内 DOI 不重复
- 当前定位：整个系统最核心的业务表

### 3.5 `paper_data`
- 用途：保存一篇文献下的多组物理参数
- 字段包括：`pressure`、`tc`、`lambda_val`、`omega_log`、`n_ef`、`s_factor`
- 支撑功能：组合页物理参数展示、首页 P-Tc 图表
- 当前定位：文献实验/理论数值承载表

### 3.6 `paper_images`
- 用途：保存文献截图
- 特点：原图和缩略图都以 BLOB 形式直接存入数据库
- 支撑功能：组合页截图展示、导出时写出图片文件
- 当前定位：文献图片附件表

## 4. 按功能的落地状态对照

## 4.1 已基本落地

以下能力已经有明确数据库承接，并能稳定支撑当前页面与主流程：

- 首页元素周期表触发检索
- 三种元素匹配模式：
  - 仅包含选择元素
  - 选择元素的组合
  - 包含所选元素
- 元素组合页文献浏览
- 关键词、年份区间、审核状态筛选
- 登录后上传 DOI、化学式、晶体结构、物理参数、截图
- 普通用户 / 管理员统一登录注册
- 超级管理员审批管理员
- 管理员审核、编辑、批量操作
- 图表展示开关
- JSON 级数据导入导出
- 前端 RIS 导出

这些能力的共同特点是：数据库中已经存在稳定的数据表、字段和查询流程来支撑它们，不只是前端设想。

## 4.2 部分落地但数据库支撑还不完整

以下能力已经有一部分底层数据，但还没有被提升为完整的业务能力：

### 更详细检索
- 当前检索主要围绕 `papers` 主表字段进行
- 支持标题、作者、化学式、年份、期刊、晶体结构、审核状态等筛选
- 但缺少更细粒度的多维组合检索体验

### 压强 / Tc 维度筛选
- 数据库中已经有 `paper_data.pressure` 和 `paper_data.tc`
- 首页图表也会消费这些数据
- 但现有检索 API 还没有把 `pressure_min/max`、`tc_min/max` 设计成正式一等筛选参数
- 目前这部分数据更多用于展示，而不是用于正式筛选

### 趋势图与检索联动
- 图表数据已经存在，且首页可以展示
- 但点击图表数据点跳转到某个文献或某个体系的闭环还没有落地

### 全局管理统计维度
- 当前后台已经能筛选、审核、编辑、控制图表显示
- 但还没有形成更系统的统计维度，例如热度、互动量、用户贡献关系等

## 4.3 尚未开始数据库建模

以下能力目前基本还停留在产品设想层，数据库没有相应表结构：

### 点赞功能
- 当前没有 `paper_likes`、`user_paper_likes` 或类似结构
- 因此无法记录谁点过赞，也无法防止重复点赞

### 评论功能
- 当前没有 `paper_comments`、`comment_replies` 等结构
- 现有 `review_comment` 仅是管理员审核意见，不是用户评论

### 弹幕功能
- 当前没有体系级消息、弹幕或互动表
- 也没有弹幕审核、透明度、显示范围等持久化设置

### 结果按热度、点赞量排序
- 当前排序主要支持 `created_at` 和 `year`
- 没有 `heat_score`、`like_count`、`comment_count`、`view_count` 之类的字段

### 数据库文件级上传下载
- 当前已实现的是 JSON 导入导出与批量表格导入
- 不是直接上传或下载整个 `.db` 文件
- 也没有数据库快照管理能力

## 5. 当前数据库设计的几个结构性短板

### 5.1 文献与提交用户没有正式外键关系
- `papers` 当前只保存 `contributor_name` 和 `contributor_affiliation`
- 没有 `contributor_user_id`
- 影响：
  - 用户改名后统计会失真
  - 同名用户会冲突
  - 无法严格追踪某篇文献的真实提交者

### 5.2 用户贡献统计依赖 `real_name`
- 当前一些统计逻辑通过 `Paper.contributor_name == User.real_name` 计算
- 这不是稳定的关系设计
- 影响：
  - 后台统计不够可靠
  - 用户关系无法作为正式分析维度复用

### 5.3 图片以 BLOB 方式存储会让 SQLite 持续膨胀
- `paper_images` 将原图和缩略图都直接写入数据库
- 对当前规模来说简单直接
- 影响：
  - 数据库文件会越来越大
  - 读写压力集中在单文件上
  - 后续迁移到对象存储会增加改造成本

### 5.4 缺少正式 migration 体系
- 当前主要依赖初始化脚本和个别专项迁移脚本
- 没有 Alembic 这类正式 schema migration 体系
- 影响：
  - 长期演进数据库结构的成本会上升
  - 一旦开始增加互动表，版本管理会更容易失控

## 6. 当前代码与产品设想的对应判断

如果从产品说明角度回看当前实现，可以这样理解：

### 6.1 当前已经是成熟主流程的部分
- 检索
- 上传
- 审核
- 图表展示控制
- 导入导出

### 6.2 当前还只是“有底层数据，但没升格为正式能力”的部分
- 基于物理参数的细粒度筛选
- 图表到检索页的联动
- 更完整的后台统计分析

### 6.3 当前还只是“设想”，不是数据库现状的部分
- 点赞
- 评论
- 弹幕
- 热度
- 社区互动沉淀
- 数据库文件级上传下载

## 7. 下一阶段更合理的数据库演进顺序

按 KISS、YAGNI 和当前项目结构，建议不要一次性引入所有互动能力，而是先补齐最关键的关系与检索短板。

### 7.1 第一优先级
- 在 `papers` 中增加 `contributor_user_id`，正式关联 `users.id`
- 在检索 API 中加入 `pressure_min/max`、`tc_min/max`
- 为常用筛选字段补充更清晰的索引策略
- 将 RIS 导出整理为后端正式接口，减少前端拼接逻辑分散

### 7.2 第二优先级
- 新增 `paper_likes`
  - 核心字段：`user_id`、`paper_id`、`created_at`
- 新增 `paper_comments`
  - 核心字段：`paper_id`、`user_id`、`content`、`created_at`、`status`
- 为 `papers` 增加派生统计字段或查询视图
  - `like_count`
  - `comment_count`

### 7.3 第三优先级
- 新增 `compound_messages` 或 `compound_danmaku`
  - 核心字段：`compound_id`、`user_id`、`content`、`created_at`、`is_visible`
- 再考虑弹幕显示配置是否需要做用户级持久化

## 8. 如何使用这份文档

如果你的目标是判断“某个功能现在到底有没有”，优先看第 4 节。  
如果你的目标是判断“数据库为什么还接不住互动能力”，优先看第 5 节。  
如果你的目标是规划下一阶段数据库演进，优先看第 7 节。

这份文档的宗旨不是替代业务模块文档，而是作为“现状 vs 设想”的判断入口，帮助你快速分辨：
- 哪些已经实现
- 哪些只是部分实现
- 哪些目前还没有开始建模
